# Team Room M3 — As Built

*Date: 2026-04-20. Frozen at commit. Future changes happen in a new as-built, not here.*

## 1. What was delivered

Milestone 3 — **"Team substrate"** (narrowed-scope ship). Two agents can direct-message each other at the daemon/plumbing layer via a new stdout verb; they share a read-write `/codebase` mount; `claude-assistant` has filesystem tools enabled via a new `allowed_tools` yaml field plumbed through the container env into the `claude-agent-sdk` Options. A conversation cap prevents runaway loops. A subscription index, built at daemon boot from each agent's `subscriptions:` yaml field, routes inbound DMs to the right agent.

Exit criteria from the spec, as adjusted during execution:

- **DM mechanism at the plumbing layer** — shipped. Agent stdout `{type:"dm", to, body}` → daemon parses via `docker-runner.parseEvent` → `turn-processor.onEvent` dm branch → per-subscriber inbound row inserted (with fresh `trace_id`, inherited `conversation_id`, and `from_agent_id` / `topic` populated) → orchestrator dispatches each subscriber's turn as usual. Self-DMs rejected with a warn; unmatched topics log `message.undelivered`.
- **Static subscriptions in `agent.yaml`** — shipped. Named-string topics only; all wake; no pattern matching. Default: each agent subscribes to its own name (`claude-assistant`, `studio-assistant`).
- **Reply routing branched by channel** — shipped. `reply` in a CLI-triggered turn creates an outbound CLI row + `message.outbound` bus event (M2 behaviour preserved). `reply` in a DM-triggered turn creates an inbound DM to `inbound.from_agent_id`, which wakes the original sender on the next orchestrator tick.
- **Conversation cap** — shipped. `TEAMROOM_MAX_TURNS_PER_CONVERSATION` env var (default `10`); cap check at `processTurn` entry; refusal records an errored turn (`status=error, error=conversation_cap`) and emits a `conversation.limit_reached` warn log.
- **Conversation_id propagation** — shipped. Fresh UUID per CLI `send`; inherited through turn creation and through DM-spawned inbounds.
- **Shared `/codebase` mount** — shipped. `TEAMROOM_CODEBASE_PATH` env var or default `<repoRoot>/codebase`; read-write mount into every agent container alongside `/AGENTS.md` and `/store`; logged at daemon boot as `codebase mount { path }` or `(none)`.
- **Claude-assistant filesystem tools** — shipped. `allowed_tools: [Read, Write, Edit, Bash, Glob, Grep]` in `agents/claude-assistant/agent.yaml`; threaded through `AgentConfig.allowedTools` → `TEAMROOM_ALLOWED_TOOLS` container env var → `agent-runtime/main.ts` parsing → `AnthropicLlmClient.Options.allowedTools`. Studio-assistant unchanged (empty allowedTools).

Exit criteria **narrowed during execution** (not delivered, by explicit decision):

- **Real-LLM agents emitting typed DM stdout events** — does not work. `src/agent-runtime/runtime.ts` wraps every LLM text response in `{type:"reply", body:<text>}`, so there's no path for an LLM agent to emit a `{type:"dm"}` stdout event from its natural-language output. See §4 for the full narrative and §5 for the path forward.
- **CLI user receives a final answer through a DM chain** — does not work. Related to the above: in a DM-triggered turn, `reply` bounces back to the DM sender, not to the original CLI user. The turn/reply primitive doesn't carry enough state for cross-channel reply routing.

Both narrowings are symptoms of one disease: the turn/reply primitive inherited from M1/M2 is the wrong metaphor for multi-agent communication. The forward direction — email-on-an-event-bus-backbone — is captured in [`docs/m3-followups.md §6`](../m3-followups.md) as the thesis for M4.

## 2. Architecture as built

### Processes and boundaries

Unchanged from M2 at the process level. Same three tiers:

- **`teamroom` CLI (host, short-lived)** — `send`, `tail`, `serve`, `status`. Generates a fresh `conversation_id` on every `send` (new in M3).
- **Daemon (host, long-lived)** — unchanged in shape. Now additionally builds an `AgentSubscriptionIndex` at boot, exposes it on `StartedDaemon`, and threads it through `OrchestratorDeps` → `ProcessTurnDeps`. Reads `TEAMROOM_CODEBASE_PATH` and `TEAMROOM_MAX_TURNS_PER_CONVERSATION` env vars with sensible defaults. `LocalModelProxy` unchanged from M2.
- **Agent container (Docker, per-turn, ephemeral)** — unchanged in shape. Now gets an additional `/codebase` mount when `codebasePath` is set, and additional env vars `TEAMROOM_ALLOWED_TOOLS` for the anthropic-provider path.

No new long-running processes. M3 principle "minimise long-running process dependencies" preserved.

### Schema (SQLite, single `data/teamroom.db`)

Migration `002_m3_team_substrate.sql` adds:

- `messages.topic` `TEXT NOT NULL DEFAULT ''` — routing key within channel. CLI messages default to empty; DMs populate with the target agent's name.
- `messages.from_agent_id` `TEXT` — sender for DMs; NULL for CLI inbounds and outbounds.
- `messages.conversation_id` `TEXT` — business-level conversation grouping. NULL for pre-M3 rows.
- `turns.conversation_id` `TEXT` — inherited from the triggering message.
- Index `idx_messages_channel_topic ON messages(channel, topic)`.
- Index `idx_turns_conversation ON turns(conversation_id)`.

`messages` and `turns` retain all M2 columns. Backwards-compatible: pre-M3 rows migrate with empty topic, NULL from/conversation; the orchestrator treats NULL `conversation_id` as "skip cap check."

### Key modules in detail

#### `src/daemon/subscriptions.ts` (new in M3)

Single class `AgentSubscriptionIndex implements SubscriptionIndex`. Constructor takes `Map<string, AgentConfig>`, iterates each agent's `subscriptions: string[]`, and builds an in-memory `Map<string, Set<string>>` keyed by `"dm:" + topic`. `lookup(channel, topic) → string[]` returns agent ids (empty array on no match). DM-channel-only in M3; no other channel keys ever populated. No hot-reload — rebuild requires daemon restart. Testable via DI: `new AgentSubscriptionIndex(new Map())` for empty-index cases.

#### `turn-processor.onEvent` branches (shipped shape)

```
- evt.type === "reply":
    if (inbound.channel === "dm"):
        - require inbound.fromAgentId != null (else warn "dm-reply.no-sender")
        - insert messages row:
            agent_id = inbound.fromAgentId
            channel = "dm"
            direction = "in"
            topic = inbound.fromAgentId
            from_agent_id = agentConfig.name (the replier)
            conversation_id = inbound.conversationId (inherited)
            trace_id = genId() (fresh)
            turn_id = null
    else (inbound.channel === "cli"):
        - insert messages row (M2 behaviour): direction="out", channel=cli, trace inherited, etc.
        - publish message.outbound bus event
        - replyCount++

- evt.type === "dm":
    - if evt.to === agentConfig.name → warn "self-dm.rejected"; return
    - subscribers = subscriptionIndex.lookup("dm", evt.to)
    - if subscribers.length === 0 → warn "message.undelivered"; return
    - for each subscriberId:
        - insert messages row:
            agent_id = subscriberId
            channel = "dm"
            direction = "in"
            body = evt.body
            topic = evt.to
            from_agent_id = agentConfig.name
            conversation_id = inbound.conversationId
            trace_id = genId() (fresh per new inbound)
            turn_id = null

- evt.type === "status" | "log": log as before (unchanged)
- evt.type === "unknown": warn (unchanged)
```

#### Conversation cap at `processTurn` entry

Placed after `turnId` generation and `turnLogger` creation, before `turnRepo.create` for the happy path:

```
if (inbound.conversationId != null
    && maxTurnsPerConversation > 0
    && turnRepo.countByConversationId(inbound.conversationId) >= maxTurnsPerConversation):
    warn "conversation.limit_reached" { conversationId, limit: maxTurnsPerConversation }
    turnRepo.create({ ..., status: "error", error: "conversation_cap", finishedAt: now })
    messageRepo.attachTurn(inbound.id, turnId)
    return
```

Pre-M3 rows with NULL `conversation_id` bypass the check (backwards compatibility).

#### Stdin envelope shape (shipped)

`turn-processor.ts` constructs per-turn:

```json
{
  "prompt": "<body>",
  "messageId": "<id>",
  "turnId": "<id>",
  "traceId": "<id>",
  "channel": "cli" | "dm",
  "from": "cli" | "<agent-name>"
}
```

Inside the container, `agent-runtime/runtime.ts` consumes the envelope and — if `channel === "dm"` and `from` is truthy — prepends `"[dm from <from>]\n\n"` to the user prompt before passing to the LLM.

### Data flow — DM round-trip (plumbing layer, shipped)

```
human → CLI send → messages (agent_id=claude-assistant, channel=cli, conversation_id=<new>)
                      ↓ orchestrator poll → processTurn (cap check OK)
            spawn claude-assistant
                      ↓
       [claude's turn runs; at the plumbing layer it can emit:]
       stdout: {type:"dm", to:"studio-assistant", body:"…"}
                      ↓ docker-runner.parseEvent recognises dm
                      ↓ turn-processor.onEvent dm branch
                      ↓ subscriptionIndex.lookup("dm","studio-assistant") → ["studio-assistant"]
             messages (agent_id=studio-assistant, channel=dm, topic=studio-assistant,
                       from=claude-assistant, conversation_id=<same>, fresh trace)
                      ↓ orchestrator poll → processTurn
             spawn studio-assistant
                      ↓
       stdout: {type:"reply", body:"…"}
                      ↓ reply branch (inbound.channel==="dm")
             messages (agent_id=claude-assistant, channel=dm, topic=claude-assistant,
                       from=studio-assistant, conversation_id=<same>, fresh trace)
                      ↓ orchestrator poll → processTurn
             spawn claude-assistant (woken by the reply DM)
                      ↓
       stdout: {type:"reply", body:"…"}
                      ↓ reply branch (inbound.channel==="dm" again)
             messages back to studio... and so on until conversation cap fires.
```

**Critical caveat this diagram hides:** in practice, real LLM agents never emit `{type:"dm"}` as a stdout event — the agent-runtime wraps all LLM text as `{type:"reply"}`. The diagram describes the plumbing as proven by `FakeRunner` scripted tests. See §4 for the full narrative.

### Config surface

New env vars (read at daemon startup in `daemon.ts`, passed through `OrchestratorDeps` → `ProcessTurnDeps`):

| Env var | Default | Validation |
|---|---|---|
| `TEAMROOM_CODEBASE_PATH` | `<repoRoot>/codebase` if it exists, else `null` | Explicit value must exist on disk (throws on startup if missing). `null` disables the mount. |
| `TEAMROOM_MAX_TURNS_PER_CONVERSATION` | `10` | Non-negative integer. `0` disables the cap entirely. Throws on invalid values. |
| `TEAMROOM_ALLOWED_TOOLS` | derived from `agent.yaml` `allowed_tools` field, joined with commas | Passed via container env, parsed inside the container into `string[]`. |

## 3. Key design decisions and their WHY

- **DM routing uses the existing DB-as-integration pattern; orchestrator untouched.**
  - **Why:** the pre-spec feasibility spike found that `orchestrator.tickOnce()` already dispatches by `messages.agent_id`. Subscription resolution happens *at DM-send time* inside `turn-processor.onEvent` (inserts one inbound per subscriber with the correct `agent_id`), so the orchestrator sees nothing new. This kept the change additive and preserved the "M1/M2 integration pattern unchanged" claim from the spec §2.

- **Subscriptions are static in `agent.yaml`, DM-channel only, no wake-flag, no pattern matching.**
  - **Why:** "see only as far as needed" principle. The M3 demo needs exactly these primitives; richer behaviour (runtime subscription changes, topic globs, pub-sub fan-out, wake-flags) is deferred with explicit triggers in `docs/m3-followups.md`. CLI routing does *not* use the subscription index — CLI `send` addresses the target agent directly, which stays asymmetric but honest.

- **Reply routing branches on `inbound.channel`; DM replies bounce back to `inbound.from_agent_id` as a new inbound.**
  - **Why:** the simplest routing rule that preserves the M2 CLI behaviour and introduces a symmetric DM behaviour. The "reply in DM context bounces to sender" rule is what makes ping-pong conversations possible — and what the conversation cap later bounds. Known limitation: a reply from a DM-triggered turn *cannot* reach the original CLI user through this rule. See §4 and §5.

- **`conversation_id` (not `trace_id`) scopes the cap.**
  - **Why:** user called out during brainstorming that using `trace_id` (observability vocabulary) for a business cap is concern conflation. `conversation_id` is a fresh business concept layered on top of the M2 observability spans. Each turn still has its own `trace_id`; conversations span multiple turns and their `trace_id` chain.

- **Cap check happens at `processTurn` entry before token mint.**
  - **Why:** zero waste on refused conversations. No routing-token allocated, no container spawned, no `turn.started` bus event emitted. The refused turn row still lands in the DB with `status=error, error=conversation_cap` so reconcile sees it as settled.

- **Cap default `N=10`, configurable via env.**
  - **Why:** five DMs each from two agents is a generous ceiling for the M3 demo without being unbounded. User's framing during brainstorming: "it can be quite blunt and rudimentary in the beginning." Blunt and rudimentary it is.

- **`/codebase` is a single uniform mount for every agent (read-write), not per-agent-configurable in M3.**
  - **Why:** user explicitly accepted "trust the agents to follow their instructions in M3" rather than enforce per-agent permissions at the filesystem level. Per-agent RO/RW flag is a cheap future addition (flip the docker `-v` arg); per-region fine-grained perms are probably never worth the engineering. `docs/m3-followups.md` tracks the trigger.

- **`codebase/` lives at the worktree root, distinct from the harness source code.**
  - **Why:** the harness is Team Room's product; `codebase/` is whatever the agents are managing. In M3 they happen to be the same repo (self-referential demo) but the architecture treats them as separate paths, and `TEAMROOM_CODEBASE_PATH` makes the real target explicit.

- **`allowed_tools` is threaded through env var, not through stdin envelope or mount.**
  - **Why:** env var is the existing pattern for per-turn container config (`TEAMROOM_PROVIDER`, `TEAMROOM_MODEL`, `TEAMROOM_AGENT_NAME`). One more env var slots in naturally. The stdin envelope is the per-turn *message* shape; tool configuration is per-container-instance, not per-message.

- **Studio-assistant gets `/codebase` mounted even though it has no tools to use it.**
  - **Why:** uniformity simplifies the daemon logic (one mounts array, no per-agent branching) and "ready for when it grows tools" future-proofs the studio-assistant LangGraph refit deferred to the memory milestone.

- **Agent-runtime prepends `[dm from X]\n\n` to the user prompt when `envelope.channel === "dm"`.**
  - **Why:** gives the LLM grounded context that a DM is different from a CLI-originated turn. The prefix is deliberately visible in the prompt text so the model can reason about it; the alternative (a structured system-prompt hint) would require more runtime plumbing without adding clarity for the LLM. This ships at the runtime layer in M3 but is orthogonal to the DM primitive's wire format — the daemon sees plain `type:"dm"` events regardless of how the agent composes its text.

- **Integration tests carry M3-expanded fixtures; existing M2 tests updated mechanically.**
  - **Why:** adding `subscriptionIndex`, `maxTurnsPerConversation`, `codebasePath` to the deps types required touching many test-fixture sites. `tsconfig.test.json` caught the ones that missed — reaffirms its value as an M2 retro action item that paid off in M3.

- **Git revert over in-place cleanup for the T22 smoke-test rollback.**
  - **Why:** the T22 addition was a good-faith attempt that the real-backend run invalidated. A `git revert --no-commit` + a follow-up narrative commit (`15b7cf1`) preserves the history of the attempt and its rationale, and makes future readers of the log able to see exactly why the DM-primitive smoke check isn't there rather than wondering if it was always missing.

## 4. Adaptations during execution

### Major: exit-scenario narrowing (the runtime-wrapping finding)

**What we thought we were building.** Spec §6.4 said the M3 exit scenario would prove:

> User → CLI → claude-assistant → reads `/codebase` → DMs studio-assistant → studio replies → claude receives the reply → claude replies to the CLI user → user sees answer via `teamroom tail`.

**What we built.** Everything up to "studio's reply wakes claude" works. The last step — "claude replies to the CLI user" — does not. Two reasons:

1. **Reply routing by channel.** `inbound.channel === "dm"` routes the reply back to the DM sender, not to a cross-channel CLI destination. Straightforward to diagnose; we chose this during brainstorming as the simpler routing rule. See §3 "Reply routing branches…" decision.
2. **The deeper gap — agent-runtime wrapping.** The smoke test at T22 exposed that `src/agent-runtime/runtime.ts` wraps every LLM text response in `{type:"reply", body:<text>}`. Claude Opus, when prompted explicitly to emit a `{"type":"dm", …}` JSON line, *did* format the JSON correctly — but it landed as text *inside* a reply body, never as a typed `dm` stdout event. **Real LLM agents cannot emit `{type:"dm"}` stdout events at all** with the current agent-runtime. Only `FakeRunner`-scripted agents can.

**Where the adaptation landed in the code:**

- `scripts/smoke-test.sh` — the `run_dm_primitive_check` function (added at T22, commit `f67ff4e`) was reverted (commit `15b7cf1`). The smoke test now exercises the M2-era checks only. The integration tests at `tests/integration/{dm-round-trip,conversation-cap,codebase-mount}.test.ts` carry M3's plumbing coverage using `FakeRunner`.
- `docs/m3-followups.md §6` — captures the email-on-an-event-bus direction as the M4 thesis. Specifically identifies the agent-runtime-wrapping finding as a key piece of evidence for the pivot.
- `docs/retros/2026-04-19-m3.md §1` and §2 — retro articulates the narrowing and the "flexibility on discovery" principle that guided the pivot.

**Why we narrowed rather than fixed.** Fixing the runtime-wrapping gap in-milestone would have required either (a) a `send_dm` tool wired through the claude-agent-sdk's tool mechanism, or (b) a runtime-side parser that extracts embedded `{"type":"dm"}` JSON from LLM text. Both are real engineering, and both point at a richer primitive (an explicit message-passing tool/API, not stdout parsing). The tool-shaped approach aligns naturally with the email-on-event-bus direction, so it's better to design it once in M4 than bolt a narrow fix onto M3.

### Minor: mid-bundle spec adaptations

Several small drifts from the plan were accepted during execution:

- **`conversationId: null` placeholders in call sites (T2+T3+T4 bundle).** The plan specified `topic: ""`, `fromAgentId: null`, `conversationId: null` at call sites in `cli/send.ts` and `turn-processor.ts` as intermediate placeholders. T8 and T9 replaced the CLI-path and turn-path placeholders with real values; T3's MessageRepo call-site fixes were spread across more files than the plan listed (notably `tests/integration/end-to-end.test.ts`), each necessary. All landed in the same task's commit or the next bundle's scope.
- **CLI outbound `conversation_id` propagation (T14+T15 bundle).** The T14 reply branch for CLI context previously set `conversationId: null` on the outbound row; the implementer noticed this and changed it to `inbound.conversationId` during T15's work, matching the DM-inbound path's inheritance. Caught via downstream code review.
- **`maxTurnsPerConversation` added to `ProcessTurnDeps` in T14 as a no-op (orchestrator passed `0`).** This split T14+T15 into two clean commits by establishing the field in T14 and activating the check in T15. The alternative — a single commit that touched both onEvent routing and cap check — would have been harder to review.
- **`tsconfig.test.json` caught 5 fixture drifts at T23.** `src/types.test.ts`, `src/daemon/turn-processor.test.ts` (3 sites), `tests/integration/end-to-end.test.ts`, `tests/integration/codebase-mount.test.ts`, and `tests/integration/conversation-cap.test.ts` each missed one or more of the new required fields introduced by T7/T15/T16. Fixed at T23 final verification; commit `04ffecc`.

### Environment adaptations

- **Fresh worktree missing `.env`.** At T1 landing, the full suite ran with 2 LM Studio test failures because the m3-team-substrate worktree didn't have a `.env` file (it's gitignored). Copied from the main worktree; one stale `CLAUDE_CODE_OAUTH_TOKEN` initially caused a 401 on Anthropic; user refreshed the token. Captured as an M3 retro §2 action item for a worktree-setup helper.
- **LM Studio multi-turn flake under vitest concurrency.** The `lm-studio-real.test.ts` multi-turn codeword test returned an empty body three times across M3 execution, always passed in isolation. Tracked in retro §2 as a fix-before-M4 investigation.

## 5. Known limitations and debts for future work

Flagged so M4 planning can pick them up deliberately. All sources linked.

### The big one

- **Real-LLM agents cannot use the M3 DM primitive.** The agent-runtime wraps every LLM output in `{type:"reply"}`; there's no path for an LLM to emit a typed `{type:"dm"}` stdout event. Plumbing works; tools to use it at the agent layer don't exist. Fix direction: email-on-event-bus with a `send-email` tool or equivalent. **Full capture: [`docs/m3-followups.md §6`](../m3-followups.md).** This is the M4 thesis.

### Retro action items (pending execution)

All from [`docs/retros/2026-04-19-m3.md §5`](../retros/2026-04-19-m3.md):

- **Full-chain feasibility-spike discipline.** Spike both the daemon-side and agent-runtime-side assumptions before committing a spec, not just the side most affected by the change. Small edit to the `writing-plans` skill expected at the next sighting.
- **LM Studio multi-turn flake.** Investigate file-level test isolation (`test.sequential` or a concurrency=1 flag) or a per-test max_tokens bump. Fix before M4.
- **Worktree `.env` helper.** Document or script the fresh-worktree env-copy step. Small but recurring.
- **M4 brainstorm opens with `m3-followups §6` as the starting context.** Don't re-derive the email direction.

### DM code kept in place

M3 landed working code for the DM primitive (stdout parsing, subscription routing, reply-branch-by-channel, `[dm from X]` prompt prefix). Even though the runtime-wrapping gap means real LLM agents can't use it today, the code stays. Rationale (per user at retro):

- The subscription index, conversation_id, conversation cap, schema columns (`channel`, `topic`, `from_agent_id`, `conversation_id`), and `/codebase` mount are all likely reused by the email mechanism.
- Working tests validate these primitives; removing now would throw away coverage.
- If M4 email supersedes DM, retire DM-specific code as an explicit task in the M4 plan — not preemptively.

### Smaller items

- **`codebase_readonly` flag in agent.yaml** — deferred per spec §1 "Out (deferred with triggers)." Trigger: a concrete need for an agent to be locked out of writes.
- **Topic globs / pub-sub fan-out** — same. Trigger: pattern subscriptions become useful.
- **Runtime subscription modification (agent-self-modifies)** — tabled during brainstorming; now subsumed by the email/inbox management vision in `m3-followups §6`.
- **Worktrees per agent for codebase editing** — deferred; trigger is two agents editing the same files concurrently.
