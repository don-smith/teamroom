# Team Room M4 — As Built

*Date: 2026-04-21. Frozen at commit. Future changes happen in a new as-built, not here.*

## 1. What was delivered

Milestone 4 — **"Agent mail — email on an event-bus backbone."** Replaces M3's DM primitive with a durable, email-shaped messaging substrate. Per-agent inboxes on the `messages` table; an in-process typed `EventBus`; a `MailDispatcher` that validates recipients, expands mailing lists, and caps threads; an HTTP MCP server on the daemon exposing `mail.*` tools (send, reply, list, get, mark_read, archive, delete); a `SessionTimerManager` that owns per-agent container lifetime with a 30-minute idle timer; `ContainerRunner` reshaped for persistent stdin streaming so the daemon pushes wake envelopes into a live container; and a second Claude-family agent (`claude-researcher`) demonstrating live agent-to-agent mail against real Anthropic.

Exit criteria from the spec, as delivered:

- **`mail.*` MCP tools** exposed via an HTTP MCP server bound to `127.0.0.1:<mailPort>` (port written to `data/teamroom-mail.port` for CLI discovery). Per-spawn `TEAMROOM_MCP_TOKEN` auth; caller scoping on every inbox operation. ✓
- **Event bus** — typed in-process publish/subscribe (`mail.delivered`, `mail.sent`, `tool.call`, `channel.cli.out`, `session.spawned`, `session.idle_exit`). Not durable; crashes drop events. DB is the durable backbone. ✓
- **Multi-recipient mail semantics** — all recipient rows share identical `to`/`cc`/`from`/`body`/`thread_id`; only `agent_id` and per-row state (`read_at`, `archived_at`, `deleted_at`) differ. Group-discussion shape preserved. ✓
- **Mailing lists** — `lists.yaml` at repo root; `MailingListRegistry` reverse-indexes subscribers at boot. Seeded with `list:harness-activity`. ✓
- **Container lifetime reshape** — `SessionTimerManager` owns the map `agentId → {containerId, stdinStream, token, timerHandle}`. Default idle 30 min; `TEAMROOM_SESSION_IDLE_MINUTES=0` disables. Daemon writes wake envelopes to stdin; stdin close → runtime reads EOF → clean exit. ✓
- **DM primitive retirement** — `{type:"dm"}` and `{type:"reply"}` stdout events removed; `src/daemon/subscriptions.ts` deleted; M3 DM integration tests retired; `turn-processor.ts` trimmed to log/status/unknown event handling only. ✓
- **Second Claude-family agent** (`agents/claude-researcher/`) subscribed to `list:harness-activity`; proven via manual test (CLI → claude-assistant → claude-researcher → reply back to CLI). ✓

Exit criteria **with partial delivery** (caveats worth knowing):

- **Mailing-list trigger fanout** — registry + trigger listener wire-up is shipped and unit-tested, but production code never publishes `turn.started` / `turn.completed` on the `EventBus` (those were M3 turn-processor events; M4's session-driven path bypasses them). The `list:harness-activity` list stays silent in live operation. Fixed in M4.5 (see §5).
- **Real-backend smoke test** — `scripts/smoke-test.sh` updated with an M4 multi-agent scenario; not run live this session. Manual three-terminal testing served that role and surfaced five P0 bugs which are all fixed.

**Test suite:** 268 passing tests (from 185 at M3 close; +83 net despite retiring ~60 M3-era tests).

## 2. Architecture as built

### Processes and boundaries

Three tiers unchanged from M3 at the process level:

- **`teamroom` CLI (host, short-lived)** — `send`, `tail`, `serve`, `status`. `send` now POSTs to `/cli/send` on the daemon when `data/teamroom-mail.port` is present (M4 path); falls back to direct DB-write when absent.
- **Daemon (host, long-lived)** — composes the M4 substrate: `EventBus`, `MailDispatcher`, `MailingListRegistry` + `MailingListTriggerListener`, `CliChannelAdapter`, `MailMcpTools`, `MailMcpServer` (on its own port; writes `data/teamroom-mail.port`), `SessionTimerManager`. The M2 `LocalModelProxy` is unchanged. The M3 orchestrator poll loop still runs — narrowed to only pick up `channel='cli', direction='in'` rows (there are none in M4; M4 mail flows through the dispatcher/bus/session-manager chain).
- **Agent container (Docker)** — now **session-scoped, not per-turn**. Container spawns on the first `mail.delivered` for an agent, stays alive across multiple wakes (each wake = one stdin envelope = one LLM turn), exits cleanly when the daemon closes stdin after idle. Injected env: everything M2/M3 had, plus `TEAMROOM_MCP_URL` and `TEAMROOM_MCP_TOKEN` so `claude-agent-sdk` can register the mail server as an HTTP MCP. Labeled `teamroom-agent=true` + `teamroom-agent-id=<name>` so a daemon restart can kill stale containers.

No new long-running processes. Minimize-process-deps memory preserved.

### Schema (`data/teamroom.db`)

Migration `003_m4_agent_mail.sql` — **additive only**. M3 columns (`topic`, `from_agent_id`, `conversation_id`) are retained as deprecated; a later cleanup migration will drop them once downstream reads confirm they're unused.

New columns on `messages`:

- `to` TEXT NOT NULL DEFAULT `'[]'` — JSON array of prefixed recipient addresses.
- `from` TEXT NULLABLE — prefixed sender (`agent:<name>`, `cli:<user>`, or the literal `system`).
- `cc` TEXT NULLABLE — JSON array; distinct-null (unset) vs empty-array (cc_all with no non-self peers).
- `subject` TEXT NULLABLE.
- `thread_id` TEXT NULLABLE — minted on fresh send; inherited on reply.
- `read_at` / `archived_at` / `deleted_at` TEXT NULLABLE timestamps.

Indexes: `idx_messages_inbox ON (agent_id, read_at) WHERE archived_at IS NULL AND deleted_at IS NULL`; `idx_messages_thread ON (thread_id)`.

### Data flow (happy path — CLI → agent → agent → CLI)

1. `teamroom send claude-assistant "..."` → CLI POSTs `/cli/send` on the daemon.
2. Daemon's `CliChannelAdapter.send()` → `MailDispatcher.sendMail()` writes one row with `channel='mail', direction='in', agent_id='claude-assistant', from='cli:don'`, publishes `mail.delivered{to:'claude-assistant'}` on the `EventBus`.
3. `SessionTimerManager.onMailDelivered` — no live session → spawn container, register session, mint MCP token, write initial wake envelope `{type:"wake", events:["mail"]}` to stdin. Timer armed at `now + 30 min`.
4. Container's `agent-runtime/main.ts` reads the wake via readline → `processWake()` invokes `AnthropicLlmClient.createMessage()` with `mcpServers: {mail:{type:'http', url, headers}}` and `allowedTools: [...base, 'mcp__mail__*']`. Claude Code CLI subprocess inside the SDK performs MCP handshake, calls `mcp__mail__mail.list`, `mcp__mail__mail.get`, decides to consult claude-researcher, calls `mcp__mail__mail.send(to:['agent:claude-researcher'], ..., threadId: T)`.
5. `MailDispatcher.sendMail` again — writes row in claude-researcher's inbox, publishes `mail.delivered{to:'claude-researcher'}`. Also publishes `mail.sent{from:'claude-assistant'}` → claude-assistant's timer resets.
6. `SessionTimerManager` spawns claude-researcher session; LLM calls `mcp__mail__mail.reply(id, body)` → dispatcher writes a row back into claude-assistant's inbox → `mail.delivered` → wake envelope pushed to claude-assistant's existing session.
7. claude-assistant's next wake sees the researcher's reply, calls `mail.list(threadId:T)` to find the original CLI mail, calls `mail.reply(<original-cli-id>, body:'final answer')`.
8. Dispatcher sees `cli:don` recipient → writes CLI outbound row (`channel='cli', direction='out'`), publishes `channel.cli.out{messageId, agentId, threadId}`.
9. Daemon's bus-to-bus bridge forwards `channel.cli.out` as a `message.outbound` event on the FileNotifyBus; `teamroom tail` (M3-shape) sees it and prints.
10. 30 min of no activity on each agent → timer fires → stdin closed → runtime reads EOF → container exits cleanly.

## 3. Key design decisions and their WHY

- **Email-on-an-event-bus as the primitive, replacing turn/reply.** M3's DM primitive surfaced that the request-response metaphor is wrong for multi-agent async communication. Email fits because every send is one-way with metadata; responses are new messages; threads are shallow groupings, not call chains. **Why:** M3 retro + `m3-followups §6` identified this as the M4 thesis; the reply-routing bounce and the runtime-wrapping gap were both symptoms of the same disease.
- **In-process `EventBus` + durable DB, not a separate broker.** No Redis, no NATS daemon, no external process. Crashes drop bus events; the DB holds mail row persistence. **Why:** `feedback_teamroom_minimize_process_deps` memory. Bus events are notifications (liveness/wake); durability belongs in the DB.
- **HTTP MCP server in the daemon (not stdio).** Containers reach it via `host.docker.internal:<mailPort>/mcp`. Per-spawn token in `x-teamroom-mcp-token` header; `SessionTimerManager` holds the token↔agentId map. **Why:** matches the M2 `LocalModelProxy` trust boundary and plumbing pattern (both are in-process HTTP servers reached from the container the same way). `claude-agent-sdk` has native `McpHttpServerConfig` support — no stdio bridge needed.
- **Per-spawn session-scoped MCP token, not per-turn.** Sessions persist across many wakes; per-turn token rotation would add work without adding trust. **Why:** aligns with the container-lifetime reshape; a single session has one stable token for its lifetime.
- **Session-driven container lifetime with 30-min idle timer.** Container spawns on first `mail.delivered`; stdin close (timer fire) → clean exit. **Why:** per-turn ephemerality (M1/M2/M3) doesn't map to "agents check mail when they want." The 30-min default matches the spec; `TEAMROOM_SESSION_IDLE_MINUTES=0` exists for debugging.
- **Dispatcher is the single writer for mail rows.** All insertion, thread-cap enforcement, and list expansion go through `MailDispatcher.sendMail()`. MCP tools, CLI channel adapter, and the mailing-list trigger listener all call into it. **Why:** `feedback_teamroom_coupling_and_extensibility` memory — atomic validation/expansion/cap enforcement is easier to reason about at one writer than scattered.
- **Multi-recipient: every row carries the full post-expansion envelope.** A list-fanout or cc recipient sees the same `to[]`/`cc[]`/`subject` that every other recipient sees. **Why:** enables Slack-style `ccAll:true` reply semantics without re-deriving the group from the DB — the reply just re-uses the envelope.
- **Thread cap at dispatcher entry, not turn-processor.** M3's `TEAMROOM_MAX_TURNS_PER_CONVERSATION` retired; replaced by `TEAMROOM_MAX_MAILS_PER_THREAD` (default 10, 0 disables). Counts all non-deleted rows in a thread. **Why:** M4 doesn't have turns in the M3 sense — mail volume per thread is the right unit. Cap error surfaces as an MCP error that the LLM can observe and recover from (archive + start new thread).
- **CLI channel via an adapter, not inline in the daemon.** `src/channels/cli.ts` is a thin `CliChannelAdapter` the daemon instantiates; `/cli/send` endpoint on the MCP server calls into it. **Why:** M3's `m3-followups §4` promised this shape when channels became first-class — Telegram/Slack/voice will slot in with the same adapter interface (followup `§2`).
- **Tail gets a bus-to-bus bridge instead of rewriting.** `teamroom tail` is an M3 artifact that listens on the cross-process `FileNotifyBus` for `message.outbound`; the M4 dispatcher publishes `channel.cli.out` on the in-process `EventBus`. Daemon subscribes to the latter and re-publishes the former. **Why:** keeps `tail` working unchanged for M4; zero-friction M3→M4 continuity for the existing user-facing surface. M4.5 is expected to retire both sides of the bridge alongside the new `watch` command (see §5).
- **M3 orchestrator poll loop kept but narrowed.** `findPendingInbound()` filters to `channel='cli'`; M4 mail rows (`channel='mail'`) never get picked up by the poll, avoiding double-processing. **Why:** cleanest transition. The poll loop is effectively vestigial in M4 but harmless; M4.5's cleanup wave is the natural time to retire it (see §5).

## 4. Adaptations during execution

- **Deferred `SessionTimerManager` wiring in `daemon.ts`** (Task 11). Shipped as "future work" with a null `tokenResolver`; 268 tests were green because `composeIntegrationHarness` wired it correctly. Manual three-terminal test caught it in ~30 s: dispatcher published `mail.delivered` with no subscriber. Fixed in `fix(m4-t11): wire SessionTimerManager into the daemon`. **Impact on the retro:** promoted composition-parity to a new memory entry (`feedback_teamroom_composition_parity`) and an M4.5 action item to extract a shared `composeMailStack(deps)` builder (or add a composition-snapshot test).
- **Hand-rolled MCP server instead of `@modelcontextprotocol/sdk`** (Task 5 choice point). Picked to avoid the stateful session-id dance of `StreamableHTTPServerTransport`. Cost: three post-manual-test shape-bug fixes — `{type:"json"}` is not a valid content type; `structuredContent` must be a plain object not an array; tool-name mangling is `mcp__<server>__<tool>` and the model silently skips tools not in `allowedTools`. All fixed; M4.5 will retrofit to the SDK (followup `§15a`). **Impact on the retro:** second sighting of "default to reference SDK for third-party protocols" — promoted to the `feedback_teamroom_protocol_sdk_default` memory entry.
- **MCP tool names required wildcards in `allowedTools`.** Not in the plan. Fixed in `fix(m4-t9): auto-allow MCP tools so agents actually call them`: `AnthropicLlmClient` now auto-appends `mcp__<name>__*` for every registered MCP server so individual agent yamls don't each have to list them. Also updated `AGENTS.md` for both Claude agents with the full `mcp__mail__mail.*` tool names so the LLM doesn't guess the prefix.
- **Tail bus-to-bus bridge.** Not in the plan. Dispatcher only published on `EventBus`; `teamroom tail` listens on `FileNotifyBus`. Fixed by extending the `channel.cli.out` payload with `messageId`/`agentId`/`threadId` and having `daemon.ts` subscribe and re-publish as `message.outbound` on the FileNotifyBus.
- **`missing_token` model-proxy log level downgrade.** Claude Code CLI (spawned by the SDK inside the container) makes an unauthenticated probe on startup. Logged at `warn` by the proxy and cluttered the daemon log. Downgraded to `debug`. Harmless; the real LLM call with our routing token follows and logs normally.
- **Test scope retired aggressively, possibly too broad.** `turn-processor.test.ts` (1000+ lines) was deleted wholesale when ~200 lines of its coverage (provider-refusal, timeout, exit-code handling) was still relevant. Noted in M4 retro §2 as a proposed rule for next time ("grep retained concerns before `git rm`ing a test file").
- **Mailing-list triggers don't fire in M4 production.** Registry + trigger listener work mechanically (integration test publishes `turn.completed` manually to exercise them) but `startDaemon` and the session-driven runtime don't publish `turn.started`/`turn.completed` on the `EventBus`. Known gap at milestone close; fix bundled into M4.5 (followup `§16`).
- **Subscription shape strict-validated.** `agent-config.ts` now throws at parse time if a subscription isn't `list:<name>`. M3 agents with bare-name subscriptions were cleared (`agents/claude-assistant/agent.yaml` → `subscriptions: []`; `agents/studio-assistant/agent.yaml` → `subscriptions: []`; `agents/claude-researcher/agent.yaml` → `subscriptions: [list:harness-activity]`).

## 5. Known limitations and debts for future work

### M3/M4-era cruft queued for cleanup in M4.5

Several legacy pieces survived M4's scope by design — kept for continuity while the new substrate proved itself. M4.5 is the natural time to retire them alongside the new surfaces that replace them. Grouping them here explicitly so the cleanup wave is scoped, not discovered piecemeal:

- **Deprecated M3 schema columns.** `topic`, `from_agent_id`, `conversation_id` on `messages`; `conversation_id` on `turns`. M4 code doesn't write to them; the `rowToMessage` mapper still populates them on reads. A `004_cleanup.sql` migration drops them once M4.5 confirms no read-path references survive (followup `§14`).
- **Orchestrator poll loop + `processTurn` + turn rows.** Preserved as the M3-era path for `channel='cli', direction='in'` messages — which M4 no longer produces (the `/cli/send` HTTP route goes straight to the dispatcher). The whole poll-driven path, `turn-processor.ts`'s remaining onEvent handling, and the `turns` table writes from that path are effectively dead in M4 operation. M4.5 is expected to retire them once no legacy CLI path remains.
- **`FileNotifyBus` + the `EventBus`↔`FileNotifyBus` bridge.** `teamroom tail` was built on FileNotifyBus (cross-process file-watching for `message.outbound` events); M4 kept it alive by bridging `channel.cli.out` into it. M4.5's planned `watch` command (SSE-style stream off the in-process `EventBus`) is a cleaner replacement for both the tail consumer and its file-notify backbone.
- **`teamroom tail` itself.** Expected to be subsumed by M4.5's `chat` + `watch` + `inbox` trio (`m4-followups §15`). The `chat` command removes the two-terminal friction (send-and-wait inline); `watch` replaces `tail` with structured observability; `inbox` replaces ad-hoc SQL queries. Once all three are in place, `teamroom tail` and its supporting plumbing (`src/cli/tail.ts`, the bridge, FileNotifyBus usage for M4 outbound) can all come out.

None of these cause operational issues today; they're visible as "commented-as-vestigial" code paths and one migration's worth of schema noise. Naming them as a group so M4.5's plan can scope the cleanup explicitly.
