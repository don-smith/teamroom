# M5 — LangGraph Agent — As Built

*Date: 2026-04-22. Frozen at commit. Future changes happen in a new as-built, not here.*

## 1. What was delivered

M5 ships a second agent runtime branch built on LangGraph.js's prebuilt `createReactAgent` + `@langchain/mcp-adapters`, shared by any agent whose provider is `lm-studio` or `ollama`. The existing `studio-assistant` migrates onto it and now participates fully in the mail substrate via MCP tools. Running during acceptance on `openai/gpt-oss-20b` through LM Studio, it successfully:

- Reads its inbox, replies in-thread, and initiates new mail to teammates.
- Lists, reads, writes, and edits files under a mounted `/codebase` and per-agent `/store` via an in-container `@modelcontextprotocol/server-filesystem` stdio MCP child process.
- Persists bounded conversation context across wakes (in-process `BaseMessage[]`, cap 40, trimmed at `HumanMessage` boundaries).

All automated acceptance criteria met: 307 tests pass across 59 files; `tsc --noEmit` clean. 23 commits on the milestone branch. Manual acceptance scenarios 1 (Claude↔Studio round-trip) and 2 (CLI↔Studio) ran end-to-end against real LM Studio. Scenario 3 (context-cap observation) is covered by unit tests; scenario 4 (Ollama smoke) was deferred — the runtime is wired for Ollama but wasn't exercised live this milestone.

The original plan's scope grew once during execution: after the core 17 tasks landed, filesystem access became a hard capability requirement and tasks 18-19 added the in-container FS MCP server + AGENTS.md update + manual acceptance. A follow-on M5.1 is already scoped for shell / git / ripgrep tooling that the filesystem-server alone doesn't cover.

## 2. Architecture as built

### Runtime layout — `src/agent-runtime/`

The M1-era shape of "one `processWake(deps: { client: LlmClient, ... })` function, provider-switched in `main.ts`" is retired. The new shape:

| File | Role |
|---|---|
| `worker.ts` | `AgentWorker` interface (`handleWake(wake): Promise<void>`), `WakeEnvelope` type, `buildWorker(): Promise<AgentWorker>` factory keyed on `TEAMROOM_PROVIDER`. Anthropic → `AnthropicAgentWorker`; `lm-studio` / `ollama` → `LangGraphAgentWorker`. Dynamic imports per provider so the unused one never loads. |
| `anthropic-worker.ts` | Wraps `AnthropicLlmClient`. Per wake: read AGENTS.md → `WAKE_PROMPT` → `client.createMessage()` → pipe text to stderr. Claude-agent-sdk handles the tool-call loop internally. |
| `langgraph-worker.ts` | Per-container stateful worker. Opens a `MultiServerMCPClient` to mail (HTTP) + filesystem (stdio); discovers tools; builds `ChatOpenAI` pointed at the daemon proxy; compiles `createReactAgent({ llm, tools, prompt: systemPrompt })`. Holds bounded `messages: BaseMessage[]` across wakes. Per-wake: append `HumanMessage(WAKE_PROMPT)` → `agent.invoke({ messages }, { recursionLimit: 50 })` → keep `result.messages` → trim at `HumanMessage` boundaries → emit last AIMessage text via `onText`. Errors piped to `onError`; worker survives. |
| `anthropic-llm-client.ts` | Unchanged behavior; absorbed the five types (`ConversationRole`, `ConversationMessage`, `LlmCreateArgs`, `LlmCreateResult`, `LlmClient`) from the retired `runtime.ts`. Only `LlmClient` has external callers now. |
| `main.ts` | 35 lines. `const worker = await buildWorker()`, then a stdin readline loop that dispatches each JSON envelope to `worker.handleWake()`. Per-wake errors logged to stderr; loop continues. |

Deleted: `runtime.ts`, `runtime.test.ts`, `session-store.ts`, `session-store.test.ts`. Their coverage ported to `anthropic-worker.test.ts` + `langgraph-worker.test.ts` with equivalent assertions.

### Provider / adapter layer — `src/model-proxy/adapters/`

Two distinct adapter classes:

- `AnthropicAdapter` — unchanged. OAuth + API-key modes; Anthropic-specific `usage` shape.
- `OpenAICompatAdapter` — renamed from `LmStudioAdapter` and parameterized by auth:
  ```ts
  type OpenAICompatAuth =
    | { mode: "bearer"; key: string }
    | { mode: "none" };
  ```
  `id` is a `Provider` passed in, so the same class serves `lm-studio` (bearer) and `ollama` (none). OpenAI-shape `usage` (`prompt_tokens` / `completion_tokens`).

`composeModelProxy` (in `src/modules/model-proxy/`) constructs both `OpenAICompatAdapter` instances (lm-studio + ollama) alongside the conditional `AnthropicAdapter`. `DaemonOptions` and `src/cli/serve.ts` thread a new `ollama: { upstreamUrl }` entry through alongside the existing `lmStudio: { upstreamUrl, realKey }`. A new `.env.example` stanza documents `OLLAMA_BASE_URL` with a `http://localhost:11434` default.

### MCP tool discovery — two servers in one client

`LangGraphAgentWorker.build()` constructs one `MultiServerMCPClient` composing:

```ts
{
  prefixToolNameWithServerName: false,  // explicit — don't rely on defaults
  additionalToolNamePrefix: "",
  mcpServers: {
    mail:       { transport: "http",  url, headers, automaticSSEFallback: false },
    filesystem: { transport: "stdio", command: "node", args: [
                    "node_modules/@modelcontextprotocol/server-filesystem/dist/index.js",
                    ...fsRoots
                  ], stderr: "inherit" },
  },
}
```

Mail lives on the host (daemon-hosted) and is reached over HTTP. Filesystem runs inside the container as a stdio child process spawned by the MCP client — it dies with the container, not a long-running shared dependency. `getTools()` flattens tool discovery across both. Seven mail tools (`mail.list`, `mail.get`, `mail.send`, `mail.reply`, `mail.mark_read`, `mail.archive`, `mail.delete`) plus thirteen filesystem tools (`read_text_file`, `write_file`, `edit_file`, `list_directory`, `search_files`, `directory_tree`, etc.).

`filesystemRoots` default to `["/codebase", "/store"]`. The worker filters them through `existsSync` at boot: if any root is absent, it's dropped (with an `[boot]`-prefixed `onError` note) rather than crashing the MCP child. If none remain, the filesystem entry is omitted entirely and the worker boots mail-only. This matters because `resolveCodebasePath` in the daemon legitimately returns `null` when `TEAMROOM_CODEBASE_PATH` is unset and no default path exists.

### Context persistence

`LangGraphAgentWorker.messages` accumulates across wakes. Trim is boundary-aware (`trimMessages()`): walks backward looking for the earliest `HumanMessage` whose retained segment is within `MAX_MESSAGES = 40`. Cutting at turn boundaries preserves the `AIMessage.tool_calls` ↔ `ToolMessage` pairing that OpenAI-compat providers require; naïve `slice(-40)` can orphan a `ToolMessage` from its originating call and cause 400-class failures on the next wake. Degenerate fallback (no boundary fits under cap) is `slice(-MAX_MESSAGES)`. Tested under both pure-AI and tool-call-bearing scripts.

`RECURSION_LIMIT` is `50` — upgraded from an initial `10` after acceptance found small-model flows exhausting the budget. `MAX_RETRIES` on the `ChatOpenAI` client is `2`.

### Container spawn

`src/agent-spec/build-spec.ts` already mounted `/codebase` (optional) and `/store` (always) for every agent regardless of provider. No spawn-time changes this milestone — the mounts were ready; what was missing was tools inside the container to reach them.

### Test harness

`langgraph-worker.test.ts` composes a real in-process MCP mail stack (`composeStorage(":memory:")` + `composeMessaging` + `composeMcpMail` + real `MailMcpServer` on an ephemeral port) and runs the actual `@modelcontextprotocol/server-filesystem` as a stdio child against a `mkdtempSync`'d root. No mocking — `fakeModel()` from `@langchain/core/testing` is the only synthesized component and is a real `BaseChatModel` subclass with `.respond()` / `.alwaysThrow()` helpers. Eight tests cover: tool discovery across both servers, wake-to-text pipeline, trim-at-40 boundary behavior, tool-call/tool-message pairing invariant, graceful degradation on missing roots, write/read round-trip through the stdio FS server, graph exceptions surviving the wake loop, repeated wake independence.

## 3. Key design decisions and their WHY

- **Extract `AgentWorker` interface rather than stretch `LlmClient`.**
  **Why:** the Anthropic path (claude-agent-sdk loops tool-calls internally — one `createMessage` call *is* a turn) and the LangGraph path (we own the messages array and the tool-loop is the graph invocation) have fundamentally different per-wake shapes. A narrower `handleWake(wake)` abstraction is honest about that asymmetry; a shared `LlmClient` was fighting the distinction. Confirmed by how cleanly the Anthropic worker reduced to a thin wrapper around the existing client while the LangGraph worker grew its own per-wake state machine.

- **Consolidate `LmStudioAdapter` into a single `OpenAICompatAdapter` with auth mode discriminator.**
  **Why:** the `see_only_as_far_as_needed` rule says formalize at N=2. Ollama is the second OpenAI-compat backend; that's the N=2 that earns the consolidation. Codex / hosted OpenAI will be the third concrete backend and will reuse the same class with `bearer` auth + a real API key — the shape already absorbs it.

- **Filesystem MCP server runs in-container as a stdio child, not on the host.**
  **Why:** the filesystem the agent can see is the one Docker mounted into its container. A host-side server would need mount translation and would drift from what the agent actually sees. Running it in-container means the agent asks about paths it literally has. This doesn't violate `minimize_process_deps` — that rule targets long-running shared services (like mail's daemon-hosted HTTP broker); a per-container stdio child dies with the container.

- **Native LangChain tools deferred to M5.1; MCP filesystem-server chosen instead for in-milestone scope.**
  **Why:** the LangChain team's own tutorials use `@modelcontextprotocol/server-filesystem` over MCP stdio. An equivalent 6-tool hand-rolled surface (~500 LoC) would have pushed scope out; adopting the reference MCP server is a drop-in. Shell access (git, ripgrep, find) has no equivalent official MCP server, so it's pushed to M5.1 with a single hand-rolled shell tool.

- **Explicit `prefixToolNameWithServerName: false, additionalToolNamePrefix: ""` on the MCP client.**
  **Why:** the schema defaults to `true` + `"mcp"` prefix, but the existing single-server M5 code worked without setting them and came back with unprefixed names (`mail.list`, not `mcp__mail__mail.list`). That worked through happenstance — either a version behavior or a quirk. Pinning both flags explicitly is a bisect-hazard mitigation: adding a third MCP server in the future won't accidentally flip tool names across the board.

- **Trim messages at `HumanMessage` boundaries, not raw count.**
  **Why:** LangGraph's ReAct executor pairs `AIMessage.tool_calls[].id` with matching `ToolMessage.tool_call_id`. A raw `slice(-40)` can cut between them, producing an orphan shape that OpenAI-compat providers (LM Studio, Ollama) reject with 400 errors. Surfaced by code review of the initial implementation; fixed with a boundary-walk algorithm plus a test that simulates tool-call round trips to prove the invariant holds.

- **Filter missing filesystem roots rather than fail boot.**
  **Why:** `resolveCodebasePath` legitimately returns `null` when no codebase is configured. Passing a missing root to `@modelcontextprotocol/server-filesystem` exits the child process with status 1 and the graph builder crashes with an opaque "Connection closed" error. Filtering with `existsSync` + a `[boot]` onError note degrades to mail-only capability gracefully while surfacing the degradation to operators.

- **`[boot]` prefix on startup warnings distinct from `[graph-error]` runtime errors.**
  **Why:** both flow through `onError` (production wires it to stderr). Mixing boot-time soft warnings with in-turn graph exceptions makes log tailing confusing. Prefixing is the cheapest disambiguation; a separate `onWarning` sink is overkill for one caller today (and `see_only_as_far_as_needed` bars us from building it speculatively).

- **`RECURSION_LIMIT: 50` not `10`.**
  **Why:** `10` was the plan's initial guess. Acceptance revealed it's too tight for the chat-via-mail → filesystem-tool flow: `mail.list` → `mail.get` → `read_text_file` → `mail.reply` is already at the boundary before the model fumbles once. Small local models fumble often. `50` matches LangGraph's own example default and leaves headroom without being so loose as to let runaways run.

- **Same `LangGraphAgentWorker` serves both `lm-studio` and `ollama`.**
  **Why:** the worker just hits a URL with an OpenAI-compat body. Whether that URL fronts LM Studio or Ollama is a daemon-side concern (proxy routing by provider). The runtime doesn't need to know. Keeps runtime code surface small; only the adapter differs (by auth mode).

- **No automated live-model E2E test.**
  **Why:** model quality is fundamentally an evals problem, not a unit-test problem. The unit harness proves the runtime can be driven (tools discoverable, messages flowing, trim correct); a live-model test would really be an eval disguised as a test, and we don't have an evals framework yet. Manual acceptance scenarios cover "does it actually work end-to-end" for this milestone. Backlog item: real evals once we have a second capability to evaluate.

- **Retire `runtime.ts` + `session-store.ts` this milestone, not later.**
  **Why:** they were explicit M1 placeholder code waiting for this milestone ("M1 deliberately uses a minimal runtime; **LangGraph is the intended long-term replacement**" — original README). Carrying them past the moment the replacement lands is cruft that future readers would misread as the current design.

## 4. Adaptations during execution

- **Planned tool-naming mismatch (`unread_only` vs `unreadOnly`).**
  What: plan prompts and `mail-mcp/server.ts` tool descriptions used snake_case `unread_only` in natural-language strings; the actual zod schema uses camelCase `unreadOnly`. Discovered during the final whole-branch code review. Fix: aligned both anthropic-worker's `WAKE_PROMPT` and the `mail.list` tool description string to `unreadOnly`. Claude had been tolerating the drift silently.
  Why: plan-time prose wasn't cross-checked against the JSON-schema-derived tool argument names. Small but real bisect hazard when debugging tool calls.

- **`createReactAgent`'s `messageModifier` → `prompt`.**
  What: the plan specified `messageModifier: systemPrompt`. The installed `@langchain/langgraph@1.2.9` marks that as `@deprecated` in favor of `prompt`. Fix: used `prompt` from the start of the LangGraph worker implementation.
  Why: the plan wrote code against type signatures known from docs/examples; implementer verified against installed `.d.ts` at build time and found the preferred form.

- **`ScriptedChatModel` fake → `fakeModel()` from `@langchain/core/testing`.**
  What: plan carried a hand-rolled `ScriptedChatModel` class for tests. It failed LangGraph's `_isBaseChatModel` type-guard because it wasn't a real subclass. Fix: used the official LangChain-shipped `fakeModel()` helper, which is a real `BaseChatModel` with `.respond()` / `.alwaysThrow()` / `.callCount` inspectors.
  Why: this is exactly what `feedback_teamroom_protocol_sdk_default.md` predicts — when a library provides an official helper, using it beats hand-rolling. The plan's hand-rolled fake was a shortcut that didn't hold.

- **Trim-at-raw-count fixed to trim-at-boundary after review.**
  What: initial `handleWake` used `this.messages.slice(-MAX_MESSAGES)`. Code review (Group D+E) correctly flagged this as unsafe against tool-call/tool-message pairing invariants. Fix: implemented `trimMessages()` walking backward for a `HumanMessage` boundary, plus a test that scripts tool-call-bearing AIMessages to prove the invariant.
  Why: the plan didn't anticipate ReAct's tool-call message-pairing semantics. Inline follow-up commit per project-local review discipline.

- **Filesystem roots filtering added after spec review of Task 18.**
  What: initial Task 18 unconditionally passed `["/codebase", "/store"]` to the FS server. Spec review confirmed the daemon legitimately supports null codebase, which would crash the server. Fix: filter roots through `existsSync`; skip the FS entry entirely if none remain.
  Why: mount-layer contract (`/codebase` is optional) wasn't encoded in the plan. Empirical test during spec review surfaced it. Fixed inline before code-quality review.

- **Scope extension mid-milestone: filesystem capability.**
  What: after the original 17-task plan landed end-to-end, the user surfaced a hard capability requirement (agents must be able to read/write the codebase mount) that had been implicit, not explicit, in the spec. Fix: added tasks 18 + 19 as an in-milestone extension, bundled `@modelcontextprotocol/server-filesystem` into studio-assistant's image, updated AGENTS.md, deferred shell/git/rg to M5.1.
  Why: the capability was on the user's mind but hadn't been pinned into the spec's "in scope" list. Honest surface during close-out; minimal re-plan; stayed in-milestone because the MCP filesystem-server is a drop-in.

- **Studio-assistant model swap during acceptance: Gemma-4 → GPT-OSS-20b.**
  What: plan selected `google/gemma-4-e4b` (~4B params). During manual acceptance it produced pseudo-code tool calls in content (e.g., `myFunction('mail_list', {'unreadOnly': true})`) instead of proper OpenAI function-calling format, hitting the recursion limit and echoing `WAKE_PROMPT` back instead of completing. Swapped to `openai/gpt-oss-20b`; all three acceptance scenarios ran cleanly.
  Why: Gemma-4-e4b is near the capability floor for this tool surface (20 tools between mail + filesystem). The runtime architecture is sound; model choice is empirical. Captured as a learning for future agent configs and for the retro.

- **`docs/ways-of-working.md` retro-ordering correction.**
  What: the reflection-rhythms table listed end-of-milestone retro before significant-work closeout. User pointed out this misses close-out learnings (as-built drift, roadmap ambiguity). Fix: reordered so retro fires LAST, with an explicit sentence about reflecting on the closeout activities themselves.
  Why: surfaced during the closeout itself. Small doc fix; durable process improvement.

## 5. Known limitations and debts for future work

Roll to `docs/roadmap.md#backlog` at milestone close:

- **Shell / git / ripgrep tooling (→ M5.1).** The filesystem MCP server exposes filename-pattern search (`search_files`), not content grep. Agents can't run git commands. Planned as a mini-milestone immediately following M5 close: one hand-rolled `run_shell` LangChain `tool()` (timeout + output cap + stdin-closed + cwd pinned) plus `apk add ripgrep git` in the studio-assistant Dockerfile.

- **Ollama acceptance scenario not run live.** Runtime is wired; no daemon restart against a real Ollama instance this milestone. Should be run next time someone is set up for it; until then, Ollama support is "compiles and starts" rather than "proven end-to-end." Test-side coverage exercises the adapter and `composeModelProxy` wiring, so code regression is caught.

- **Model-size vs. tool-surface floor.** Gemma-4-e4b (4B) isn't capable enough to reliably drive a 20-tool ReAct surface; GPT-OSS-20b works cleanly. Somewhere between 4B and 20B there's a reliability floor we haven't characterized. Worth a follow-up investigation if we add more small-model agents, or skip and just recommend "20B+ minimum for agents with full tool access."

- **`agents/README.md:47` lumps `claude-researcher` tools with `claude-assistant`.** Researcher's `agent.yaml` declares `[Read, Grep, Glob, Bash]` — no Write/Edit. README line shows the assistant's superset. User elected to leave this (they don't want the README tracked per-agent-config). Flagged for awareness; not a blocker.

- **`docs/runbooks/agent-onboarding.md` is M3-era.** Still documents `provider: anthropic | lm-studio` (no `ollama`), wrong CLI subcommands (`teamroom send --agent`, `teamroom tail` — neither exists), references "M3+ skill assignments." User elected to push the rewrite to the next milestone touching agent onboarding.

- **No automated live-model E2E test.** Manual acceptance only. Evals framework is the long-term answer; no trigger date today.

- **Per-wake `AbortSignal` wall-clock cap.** Deferred until a runaway is observed in production. `RECURSION_LIMIT: 50` bounds step count; wall clock can still run away on a slow upstream.

- **Generic `openai-compat` provider.** Defers until third concrete backend (Codex / hosted OpenAI / vLLM) forces the shape. Until then `ollama` is the second instance that earns the adapter consolidation.

- **`LM_STUDIO_API_TOKEN` optionality.** Still required by `serve.ts`. After M5 it's only meaningful when LM Studio is token-protected. Relax when onboarding friction surfaces.

- **Two `WAKE_PROMPT`s in the messages array on repeat wakes.** Every wake pushes the same literal `HumanMessage(WAKE_PROMPT)` to the in-process array. A small model seeing two identical directives in history may loop or fumble. Not observed in GPT-OSS-20b acceptance; would be a candidate cause if multi-turn small-model flows start failing. Possible fix: per-wake trace id in the prompt or a fresh messages array per wake.

- **Dead exports in `anthropic-llm-client.ts`.** `ConversationRole`, `ConversationMessage`, `LlmCreateArgs`, `LlmCreateResult` have no external consumers after the refactor. Candidates for removal next time the file is touched.

- **`adapters as Record<Provider, ProviderAdapter>` cast at `src/modules/model-proxy/model-proxy.ts:50`.** Laundering through an `as` to satisfy `LocalModelProxy`'s constructor. Fixable by widening the constructor to `Partial<Record<Provider, ProviderAdapter>>` or restructuring the compose function. Not a blocker; noted for next refactor.
