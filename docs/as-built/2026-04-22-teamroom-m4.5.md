# M4.5 — AI-Native Harness — As Built

*Date: 2026-04-22. Frozen at commit. Future changes happen in a new as-built, not here.*

## 1. What was delivered

M4.5 reshapes Team Room around a **channel architecture** and a **composition refactor**. The CLI flows through a daemon-owned WebSocket as the first concrete instance of a generalizable channel pattern; `startDaemon` becomes a thin top-level composer over eight named modules under `src/modules/`; `composeIntegrationHarness` calls the same composers, so the M4 drift bug class is structurally impossible to recur (composition parity by construction). The mail-MCP server is retrofitted onto `@modelcontextprotocol/sdk`. The legacy CLI orchestration path (`Orchestrator`, `turn-processor`, `reconcile`, `FileNotifyBus`, `tail`, `/cli/send` route, the Turn DB subsystem) is fully removed. Three new CLI commands ship — `chat` (interactive REPL), `inbox`, `thread` — alongside a refactored `send`.

Spec exit criteria all met. The seven manual acceptance scenarios were exercised through the new CLI commands during close-out (chat-as-thread, agent-to-agent, ccAll group thread, thread cap, idle exit, daemon-restart, self-mail, invalid recipient). Test suite: 295 passing across 51 files; `tsc --noEmit` clean. 61 commits on the milestone branch; daemon.ts went from 322 → 266 lines despite gaining two new external surfaces (chat + mail WebSockets) and adopting the compose-pattern.

## 2. Architecture as built

### Module layout (`src/modules/`)

Eight modules. Each exposes a `compose<Name>(deps): <Name>` factory and a `<Name>` interface for its returned shape.

| Module | Owns |
|---|---|
| `observability` | `Clock`, `JsonLinesLogger`, log file path |
| `storage` | `Db` connection, migrations runner, `AgentRepo`, `MessageRepo` |
| `messaging` | `EventBus` |
| `mcp-mail` | `MailDispatcher`, `MailingListRegistry`, `MailingListTriggerListener`, `MailMcpTools`, `MailMcpServer` |
| `model-proxy` | `TokenRegistry`, provider adapters, `LocalModelProxy`, OAuth helpers |
| `session-management` | `DockerRunner`, `SessionTimerManager`, the three bus subscriptions (`mail.delivered`, `mail.sent`, `tool.call`) |
| `channels` | `ChannelRegistry`, `ChatServer` (chat WebSocket on its own port), `chat` protocol types |
| `mail` | `QueryServer` (read-only mail WebSocket on its own port), query protocol types |

Dependency direction (acyclic):

```
observability  ← (everyone, when they need a logger or clock)
storage        → observability
messaging      → observability
mcp-mail       → storage, messaging, observability
model-proxy    → observability
session-mgmt   → messaging, observability  (+ DockerRunner)
channels       → messaging, mcp-mail, storage, observability
mail           → storage, observability
```

The notable arrow: **`channels` → `mcp-mail`**. Inbound CLI chat goes through `MailDispatcher.sendMail()` rather than around it — the dispatcher is the single entry point for creating mail rows and publishing dispatch events, regardless of whether mail originates from an agent (via MCP) or from the CLI (via the chat WebSocket).

### Daemon composition

`src/daemon/daemon.ts:startDaemon` is now a 13-section composer. Sections are numbered in source comments to make ordering visible:

```
1.  FS setup + PID file
2.  Observability (compose)
3.  Stale-container cleanup
4.  Storage (compose) + agent discovery
5.  Messaging + mcp-mail (compose)
6.  Model proxy (compose)
7.  Codebase-mount resolution
8.  Mail MCP server (with late-bound token resolver)
9.  Session management (compose) + token resolver rebind
9a. Bus-event observability subscriptions (mail.delivered/mail.sent/tool.call → log)
10. Channels (compose) + ports/chat.port
11. Mail query server (compose) + ports/mail.port
12. Stop orchestration (ingress-first: channels → mail → mail-MCP → model-proxy → storage)
```

Side-effect-only startup helpers (`safetyNets`, `discoverAgentConfigs`, `resolveCodebasePath`, `killStaleTeamroomContainers`) stay as direct calls rather than modules — they have no exports anyone needs to depend on.

The integration test harness (`tests/integration/helpers.ts:composeIntegrationHarness`) calls 6 of the 8 modules with test-friendly substitutions (in-memory DB, `ControllableClock`, `FakeRunner`, `manualTimers`, deterministic `genId`). It deliberately skips `composeObservability` (tests need a controllable clock that the production observability module doesn't expose) and `composeModelProxy` (FakeRunner-based tests don't make real LLM calls). The other six modules are byte-equivalent calls — drift between test and prod is structurally impossible.

### External surfaces

The daemon now opens **three external-facing ports** plus the model-proxy internal port:

| Port file | Surface | Protocol | Bound to |
|---|---|---|---|
| `<dataDir>/ports/mail-mcp.port` | Agent-facing MCP | HTTP via `@modelcontextprotocol/sdk` `StreamableHTTPServerTransport` | (whatever the daemon binds — typically all interfaces) |
| `<dataDir>/ports/chat.port` | CLI / future channel clients | WebSocket (bidirectional, bus-native) | `127.0.0.1` |
| `<dataDir>/ports/mail.port` | CLI / read-only inbox+thread queries | WebSocket (request/response) | `127.0.0.1` |
| (no port file) | Local model proxy | HTTP, container-injected URL | `127.0.0.1` |

Agent containers receive `TEAMROOM_MCP_URL` via env-var injection at container start (the daemon controls container env). User-started CLI tools read the port files. The `ports/` folder convention replaces the M4-era one-off `teamroom-mail.port`.

### Channel architecture

A **channel** is a routing prefix bound to an authentication policy. The current model:

- `ChannelRegistry` (in `src/modules/channels/channel-registry.ts`) holds the names of valid channels (today: just `cli`). Throws on duplicate registration; consulted by `ChatServer.handleConnection` to validate `register` messages.
- `ChatServer` (in `src/modules/channels/chat-server.ts`) is the bus↔WebSocket bridge. Clients `register` for a `channel:<name>:<external-id>` address, then `publish` inbound mail (server calls `dispatcher.sendMail` with `from: channel:<channel>:<external-id>`). Outbound mail addressed to `channel:cli:*` flows back via the dispatcher's `channel.cli.out` event, which `ChatServer.routeCliDelivery` forwards as `mail` server messages to the matching connected client.
- The CLI command (`teamroom chat`/`send`/`inbox`/`thread`) is a separate process that connects to the WebSocket as a client. Future Telegram/Slack gateways will be separate processes following the same pattern — they speak Telegram/Slack on one side and the chat WebSocket on the other.

The **chat WebSocket protocol** (`src/modules/channels/protocol.ts`):
- Client→daemon: `register` (claim a channel address), `publish` (inbound mail).
- Daemon→client: `mail` (outbound mail addressed to this client), `event` (bus events; not yet exercised in production), `error` (structured `{code, message}`).

The **mail WebSocket protocol** (`src/modules/mail/protocol.ts`) is request/response:
- Client→daemon: `query` with `query: "inbox" | "thread"` + params.
- Daemon→client: `result` with rows, or `error`.

### Address scheme

Hierarchical, three top-level kinds:

```
agent:<name>                       e.g. agent:claude-assistant
list:<name>                        e.g. list:harness-activity
channel:<channel>:<external-id>    e.g. channel:cli:don, channel:telegram:12345
```

`Address` discriminated union is in `src/mail-dispatcher/address.ts`. **Lenient parse / strict deliver**: `parseAddress` accepts any well-formed address regardless of channel-registry state; `MailDispatcher.sendMail` rejects unknown agent or list recipients at delivery time. Channel addresses are not yet rejected at the dispatcher (see §5 — `ChannelRegistry` → dispatcher wiring is in the Backlog).

### CLI surface

| Command | Behavior | Transport |
|---|---|---|
| `teamroom serve` | Start daemon | (process) |
| `teamroom status` | Print PID file + each port file | reads `ports/` |
| `teamroom send <agent> "<text>"` | Fire-and-forget single message | chat WebSocket (publish, brief settle, close) |
| `teamroom chat <agent> ["<text>"]` | Interactive REPL: `you:` prompt, blank-line separators, `/quit` / `/exit` / EOF / SIGINT to exit, threadId reused within session | chat WebSocket (interactive, opt-in `interactive: true`) |
| `teamroom inbox <agent>` | Print inbox rows as JSON-Lines | mail WebSocket |
| `teamroom thread <id>` | Print thread rows as JSON-Lines | mail WebSocket |

Removed: `teamroom tail`. The `runQuery` helper in `src/cli/query-client.ts` is shared by `inbox` and `thread`.

### Configuration via `.env`

`teamroom serve` calls `loadEnvFile(cwd)` at startup, which injects every `KEY=value` from `.env` into `process.env` (without overriding shell-set values). Documented tunables (in `.env.example`):

- Credentials: `LM_STUDIO_API_TOKEN`, `LM_STUDIO_BASE_URL`, `CLAUDE_CODE_OAUTH_TOKEN`, `ANTHROPIC_API_KEY`
- Daemon tunables: `TEAMROOM_SESSION_IDLE_MINUTES` (default 30), `TEAMROOM_MAX_MAILS_PER_THREAD` (default 40), `TEAMROOM_CODEBASE_PATH`, `TEAMROOM_USER`

The daemon logs the resolved `idleMinutes` value at startup so configuration drift is one log line away from being diagnosed.

### Database

| Migration | Purpose |
|---|---|
| `001_initial.sql` | (M1) base schema |
| `002_m3_team_substrate.sql` | (M3) topic / from_agent_id / conversation_id |

`MessageRepo` exposes the read methods consumed by the channels module, the mail query server, and the integration test harness: `findById`, `listInbox`, `listThread`, `listCliOutbound` (the last is integration-test-only via `tests/integration/cli-test-helper.ts`).

## 3. Key design decisions and their WHY

- **Channels as a generalizable architecture, not a CLI hack.**
  CLI is the first concrete channel; Telegram/Slack/voice will follow the same shape. **Why:** the M4 CLI plumbing was wedged into the wrong places (DB-direct write in the test harness, `/cli/send` bolted onto the mail-MCP server, `tail` watching FileNotifyBus). The brainstorm (memory: `feedback_teamroom_coupling_and_extensibility`) reframed the work: the architectural pattern is the deliverable, not just a polished CLI.

- **Composition refactor over snapshot test for §15b.**
  Both `startDaemon` and `composeIntegrationHarness` call the same `compose<X>` functions; drift is structurally impossible. **Why:** the M4 retro identified that the missing `SessionTimerManager` bus subscriptions (which the integration harness installed inline but `startDaemon` did not) were invisible to 268 passing tests. A snapshot test would have caught this specific bug after the fact; refactoring to a shared compose graph prevents the *class* of bug. Memory: `feedback_teamroom_composition_parity`.

- **MCP SDK retrofit despite M4 having a working hand-rolled server.**
  Replaced `src/mail-mcp/server.ts`'s hand-rolled JSON-RPC with `@modelcontextprotocol/sdk`'s `McpServer` + `StreamableHTTPServerTransport`. **Why:** M4 burned three post-test fix commits inventing envelope shapes (`{type:"json"}` content, `structuredContent` arrays, tool naming). The protocol drifts; the SDK absorbs the drift. Memory: `feedback_teamroom_protocol_sdk_default`.

- **Two WebSocket ports for chat and mail rather than one.**
  Separate ports, separate port files. **Why:** they're different surfaces — chat is bus-native bidirectional; mail is request/response read-only (with future RW). The user explicitly chose split during brainstorm: "I might separate those out at some point. So it feels like and it's also easy to believe that I might separate those out at some point." Two consistent technologies (both WebSocket) with same-tech-different-port preserves future flexibility.

- **Per-request `McpServer + StreamableHTTPServerTransport` construction.**
  The SDK's stateless transport throws on second use. **Why:** verified against `node_modules/@modelcontextprotocol/sdk/dist/esm/server/webStandardStreamableHttp.js:138-140`: `if (!this.sessionIdGenerator && this._hasHandledRequest) throw new Error("Stateless transport cannot be reused…")`. The SDK author's stated rationale is to avoid message-ID collisions between clients. Per-request construction is a few extra ms; correct and matches SDK intent.

- **Low-level `setRequestHandler(CallToolRequestSchema, ...)` instead of `mcp.tool()`.**
  Bypasses the SDK's `registerTool` to access raw `request.params.arguments`. **Why:** without a Zod schema, `registerTool`'s callback gets no args. We don't yet have Zod schemas for our mail tools (the existing `MailMcpTools` does its own validation downstream). The low-level path preserves behavior; adopting Zod is in the Backlog (would also clean up the descriptor table and gain SDK-native validation).

- **`channel.cli.out` event remains CLI-specific (deliberate scope).**
  The dispatcher publishes `channel.cli.out` for `channel:cli:*` recipients; `ChatServer.routeCliDelivery` subscribes specifically. **Why:** generalizing to `channel.<name>.out` (or a single `channel.out` with channel name in payload) is a small change but premature without a second concrete channel to push on the design. Boundary is clean enough for the cleanup when Telegram/Slack land. In the Backlog.

- **Ingress-first stop ordering.**
  `stop()` shuts down external surfaces (channels → mail → mail-MCP) before their dependencies (model-proxy → storage). **Why:** any late-arriving inbound during shutdown can't land in a half-torn-down substrate. Surfaced in Group 14 review; preserved through every subsequent change.

- **`teamroom send` keeps a 30 ms post-publish sleep.**
  The chat protocol has no acknowledgement frame; the brief sleep ensures the publish is processed before the WebSocket close. **Why:** local-loopback only, brittle in slow environments but functional today. A proper `ack` frame is in the Backlog (would replace the sleep with a real wait).

- **`src/channels/cli.ts` (`CliChannelAdapter`) moved to `tests/integration/cli-test-helper.ts`.**
  The class only existed to inject CLI-flavored mail directly into the dispatcher in integration tests; production CLI flows through the chat WebSocket. **Why:** "production code under `src/` that only exists to support tests" was a smell flagged by the Group 21 review. Moving it makes the test-only purpose honest; `src/channels/` was deleted.

- **Legacy Turn DB subsystem fully removed; model-proxy `turnId` retained.**
  The legacy Turn concept (DB table, `TurnRepo`, `Message.turnId`, `teamroom status` counts) was driven entirely by the now-removed `Orchestrator`. **Why:** zero live writers; status counts always 0 for new deployments after M4.5. Migration `005` drops the table + column. The model-proxy's `turnId` field (in `TokenRegistry` entries) is a span/trace identifier — same name, completely different concept; alive and unchanged.

- **Default `maxMailsPerThread` raised from 10 to 40.**
  Acceptance feedback: 10 is too tight for typical multi-message agent exchanges (agents stream multi-message replies; each adds to the thread). **Why:** the cap exists to prevent runaway threads, not to cap normal collaboration. 40 gives meaningful headroom; configurable via env var.

- **`.env` is now a general dotenv loader, not a four-key allowlist.**
  Replaced `readEnvFile(dir, keys)` with `loadEnvFile(dir)` that injects all `KEY=value` pairs into `process.env` (without overriding shell-set values). **Why:** the allowlist's "security" benefit didn't earn its cost. Users naturally expected `.env` to control any tunable. Discovered when `TEAMROOM_SESSION_IDLE_MINUTES=1` in `.env` was silently ignored during acceptance.

- **Single working-memory location: `tabled.md` for everything.**
  Per-milestone followup files (`m3-followups.md`, `m4-followups.md`, `m4.5-followups.md`) retired in favor of `docs/tabled.md` for both epiphanies and tabled follow-up work. At milestone close: still-relevant items roll into `docs/roadmap.md#backlog`. **Why:** three followup files made it unclear at a glance which items were still outstanding. One working-memory location, one Backlog as source of truth, one milestone-close consolidation pass.

## 4. Adaptations during execution

- **Spec said `queries` module for the read-only WebSocket; renamed to `mail` mid-brainstorm.**
  The user found "queries" too generic. Renamed in commit `cd424bf` before implementation began. The module is distinct from `mcp-mail` — `mcp-mail` is the in-process mail system; `mail` is the external read view onto it.

- **Spec said `chat` exits on "first reply"; reshaped to interactive REPL with explicit-only exit.**
  User pushback during brainstorm: "I'm quite happy for that to be explicit. So normally I would just do a slash quit or a slash exit." Captured in commit `cd424bf`. The implementation tracks the session's `threadId` from the first incoming `mail` frame and reuses it for subsequent publishes — chat session = single logical thread.

- **Plan said the address-scheme migration would be a TS-extended migrator; implementation kept the existing SQL-only migration pattern.**
  Plan flagged: "the spec described the migration as TS code in the migrator. The plan uses plain SQL with SQLite JSON1." The plan's choice prevailed; SQLite ≥3.35's `ALTER TABLE … DROP COLUMN` (which migration 005 also uses) made the SQL-only pattern viable across all M4.5 schema work. No migrator changes needed.

- **`mail.delivered` event doesn't carry channel-recipient mail.**
  Plan sketch had `ChatServer` subscribe to `mail.delivered` for all channel routing. Verified during Group 13 implementation: dispatcher publishes `mail.delivered` only for agent recipients; channel recipients fire `channel.cli.out` (M4-era event name). Implementation pivoted to subscribe to `channel.cli.out` and the dispatcher was extended to carry `from`/`to` on the event payload + on the cli row. Documented in commit `8b16460`.

- **Integration harness sync→async conversion (Plan Task 17 / Group 11).**
  `composeIntegrationHarness` was sync at refactor time; adding `composeChannels` (async) and `composeMail` (async) forced the conversion. Eight call sites across three test files updated to `await composeIntegrationHarness(...)`.

- **Group 17 (inbox + thread CLI) created a bisect hazard via retroactive helper extraction.**
  Commits `11c7023` and `81605da` import from `./query-client.js` which doesn't land until commit `5854239`. The intermediate commits don't compile in isolation. Branch-end state is correct; the process lesson is captured in the retro for next time. (When a retroactive refactor extraction happens, either land the helper in commit 1 or genuinely defer the extraction.)

- **`StorageLike`/`ClockLike`/`LoggerLike` structural types in `discoverAgentConfigs` were removed in cleanup.**
  Initial implementation used local structural types claiming to avoid a circular dep that didn't actually exist. Group 10 review flagged it; commit `16e52a9` switched to the concrete module types.

- **Group 21 reviewer flagged `NotifyBus` + `InMemoryBus` as orphans after `FileNotifyBus` deletion.**
  Group 22 deleted both. `MessageRepo.listCliOutbound` was retained (still used by integration tests via `cli-test-helper`).

- **MCP server "renamed" `MailMcpServerOpts` → `MailMcpServerDeps` during the SDK retrofit.**
  No external importers; reviewer noted the inconsistency with the surrounding codebase's `Opts` naming (e.g., `MailDispatcherOpts`). Decision deferred — both names appear in the codebase; a unification pass is in the Backlog.

## 5. Known limitations and debts for future work

The full set is in [`docs/roadmap.md#backlog`](../roadmap.md#backlog). Items most likely to bite the next milestone:

- **`channel.cli.out` is CLI-specific** — `ChatServer.routeCliDelivery` hard-codes `c.channel === "cli"`. Generalize when the second channel arrives.
- **`ChannelRegistry` is not consulted by the dispatcher** — channel addresses bypass the strict-deliver check that `agent` and `list` addresses get. Wire it through `MailDispatcherOpts.knownChannels` (parallel to `knownAgents` / `knownLists`).
- **`teamroom send` 30 ms sleep** — protocol has no `ack` frame. Brittle on slow daemons.
- **`ccAll` defaults to false on `mail.reply`** — multi-party threads silently drop participants when an agent replies. Acceptance found this; spec for `mail.reply` should document the default and probably flip it.
- **Cap-warning feature** — when threads approach the cap, agents have no signal until they hit it. Last 10 messages should carry `messagesRemaining` in the dispatcher response.
- **CLI users can't add `cc` recipients** via the chat REPL — agents can but humans can't.
- **Mailing-list system unverified end-to-end live** — infrastructure works, integration test passes (publishes events manually), but `SessionTimerManager` doesn't publish `turn.started` / `turn.completed` in production. Bundled with the future "lists" milestone.
- **Model-proxy log readability** — verbose JSON-Lines with embedded request/response bodies. Hard to tail raw.
- **`teamroom status` is minimal** — PID + port files only. Could surface active sessions, recent activity, last mail delivered.
- **`MailMcpServerOpts` vs `MailMcpServerDeps` naming inconsistency** — pick one convention across the codebase.
