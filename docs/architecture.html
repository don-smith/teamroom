Architecture & design reference · snapshot

A team of colleagues, not a bigger agent.

Team Room is a multi-agent harness shaped like a software delivery team. Each agent has its own identity, container, mounts, credentials, and tools; they coordinate through explicit, typed substrate — a mail system on an event-bus backbone — rather than implicit shared state.

Latest milestone M5 — LangGraph runtime
Active agents studio-assistant · claude-assistant
Host language TypeScript (strict) · Node 22+
Container runtime Docker
Persistence SQLite (in-process)
This is a snapshot. The authoritative current state lives in docs/as-built/ (each milestone freezes its architectural reality there) and docs/roadmap.md (what's next). When this page disagrees with those, they win — re-cut this page.

The thesis

One assistant has limits a team doesn't.

The mental model is deliberate: not "a bigger agent" but "a team of colleagues" — each narrow, each specialized, each accountable for its own work, coordinating through explicit team infrastructure. That word — explicit — is the line between Team Room and a swarm.

The honest finding from the multi-agent literature is that group chat, hierarchical handoff, and debate rounds rarely earn their token cost. What does earn it: narrow specialists with clear permission boundaries, typed shared state with a reducer, and critic/reviewer loops. Team Room's design is shaped around those findings rather than around the more theatrical patterns.

A retrospective is a structured message sent to the team topic. No hidden coordination layer. Team ceremonies are messages, not magic. — design principle #10

Design principles

Ten rules that haven't moved.

These were locked at the M1 spec and have survived every milestone since. Each card carries the rule and the why — the reason matters more than the words because the why is what lets you judge edge cases later.

01

The orchestrator stays procedural.

Why: no LLM in the routing hot path. Deterministic, debuggable, replayable. All intelligence lives in containers; the daemon is the boring conveyor belt.

02

Agents run in isolated containers.

Why: a fresh container per agent process gives filesystem, credential, and blast-radius isolation by construction. Borrowed from NanoClaw; unchanged.

03

Per-agent isolation by default.

Why: own folder, own memory namespace, own tool config, own credentials. Sharing is a deliberate decision, never the default.

04

Shared resources are explicit and typed.

Why: the codebase mount, the event bus, the mail substrate — each is a first-class primitive with a declared schema. Never an untyped folder you hope agents agree on.

05

Observability is a slice of every milestone.

Why: not a milestone of its own. Each subsystem ships with logs, span-shaped events, and trace IDs from the day it lands.

06

Permission scoping at the credential layer.

Why: the model proxy enforces "agent X may call provider Y." Defense at the boundary, not defense-in-depth scattered through every tool.

07

Multi-model from the start.

Why: agents pick a provider per turn; the proxy resolves the routing token. The Anthropic / LM Studio / Ollama split exists because that contract was honored from M2.

08

Evaluations are per-agent.

Why: each agent has its own scenarios and regressions. Team-level evals compose from agent-level ones — never the other way around. (Substrate landed; harness deferred to M9.)

09

Self-learning is bounded.

Why: agents propose changes; changes are applied explicitly with outcome tracking. No silent self-modification, ever. (Substrate; M10.)

10

Team ceremonies are messages, not magic.

Why: a retro is a structured message on the team topic. Coordination always flows through the visible substrate — there is no hidden layer.

Five additional rules locked from the M1 spec

Deliberate coupling and extensibility.

State what is shared and what is isolated at every boundary. Coupling is a first-class architectural concern, not an emergent property.

Minimize long-running process dependencies.

Prefer in-process or per-container children over separate services. SQLite over Postgres, an in-process EventBus over a broker, an in-container MCP child over a host-side daemon.

See only as far as needed.

Don't formalize on N=1. The OpenAI-compat adapter was extracted only when Ollama arrived as N=2. A generic openai-compat provider waits for N=3.

Nothing silent, nothing inconsistent, nothing crashes.

Global safety nets in the daemon; containers run to completion or the daemon kills them. Errors surface; degraded modes announce themselves; hung work is bounded.

Design for testability via DI.

Every effectful dependency behind an interface; tests use real in-memory implementations, never vi.mock. The integration harness composes the same modules production does.

Default to the reference SDK for any third-party protocol.

MCP, OAuth, OpenAI compat: protocols drift; SDKs absorb the drift. Hand-roll only with a documented blocker-grade reason.

System architecture

The host / container split.

The single most load-bearing seam in Team Room is the line between the long-running host daemon and the per-agent containers. Every other boundary defers to it. The daemon owns the database, the bus, the dispatcher, the model proxy, and the WebSockets the world reaches in through. Containers own the LLM and its tools, communicating outward only through MCP (mail, filesystem) and HTTP (model proxy).

Figure 1. Eight composed modules on the host; two MCP clients plus an LLM client per container. The dispatcher is the single entry point for every mail row, regardless of whether the source is an agent (via MCP HTTP) or a human (via the chat WebSocket). Containers never see real model credentials — only an ephemeral routing token the proxy translates. Outbound CLI delivery goes back through the bus's channel.cli.out event, which ChatServer subscribes to. Docker's spawn arrow is dashed because it crosses the trust boundary; everything inside the container is opaque to the host beyond the stdin/stdout protocol.

Why the host / container line is so load-bearing

The container contract is language-agnostic. The daemon treats agent-runtime/ as opaque beyond the stdin/stdout JSONL envelope protocol. That gives Team Room two important affordances: a Python or Rust runtime can replace the TypeScript one tomorrow without touching the daemon, and the credential blast-radius is bounded at a real OS process boundary, not a soft language one.

Subsystems & responsibilities

What each piece owns.

Every multi-file module under src/ declares its contract in a README following a fixed shape: what it is, where it runs, who uses it, what it depends on. Below: the fast tour, in roughly the order the daemon composes them at boot.

daemon src/daemon/

host · long-running

The composition root. startDaemon wires eight modules in a fixed order and opens four ports (mail-MCP, model-proxy, chat WS, mail WS). Procedurally boring on purpose — the daemon contains no LLM in the hot path. Global safety nets keep it alive through unhandled exceptions.

Composes
observability → storage → messaging → mcp-mail → model-proxy → session-management → channels → mail
Invariants
nothing silent · nothing inconsistent · nothing crashes
Entry
cli/serve.ts (the daemon has no main.ts of its own)

agent-runtime src/agent-runtime/

container · per agent

The shim that runs inside each agent container. Reads JSON wake envelopes from stdin one per line and dispatches to worker.handleWake(). Two worker implementations today, picked by TEAMROOM_PROVIDER.

Anthropic
AnthropicAgentWorker — wraps @anthropic-ai/claude-agent-sdk; the SDK handles the tool-call loop internally.
LangGraph
LangGraphAgentWorker — prebuilt createReactAgent + @langchain/mcp-adapters; holds bounded BaseMessage[] across wakes (cap 40, trim at HumanMessage boundary).
Boundary
language-agnostic — daemon never imports from this module.

mail-dispatcher + mail-mcp src/mail-dispatcher/ · src/mail-mcp/

host

The mail substrate is Team Room's universal coordination primitive. MailDispatcher is the single entry point for creating mail rows: agents reach it via MCP tools (mail.send, mail.reply, …), the chat WebSocket reaches it via publish. Lenient parse, strict deliver: any well-formed address parses; unknown agent or list recipients are rejected at delivery.

Addresses
agent:<name> · list:<name> · channel:<chan>:<ext-id>
Tools
list, get, send, reply, mark_read, archive, delete (7)
Cap
40 mails per thread (TEAMROOM_MAX_MAILS_PER_THREAD)

mailing-lists src/mailing-lists/

host

Loads lists.yaml into a registry and subscribes a TriggerListener to bus events that should fan out as mail to list:<name>. Mechanically functional; in live operation only one list (list:harness-activity) is seeded, and the publishers that would feed it (turn-event publication) aren't wired yet — see roadmap.

session-manager src/session-manager/ · modules/session-management/

host

Subscribes to mail.delivered on the bus. For each delivery to an agent address, ensures the container is up (spawning if needed via ContainerRunner), pushes a wake envelope down its stdin, and arms the SessionTimerManager to close stdin after idle minutes (default 30, tunable). One container per agent, kept warm across turns, killed cleanly on idle.

Subscribes
mail.delivered · mail.sent · tool.call (observability)
Idle timer
TEAMROOM_SESSION_IDLE_MINUTES=30

model-proxy src/model-proxy/ · src/model-proxy/adapters/

host · 127.0.0.1

An in-daemon HTTP listener bound to localhost on an OS-assigned port. Containers send all model traffic to it carrying only an ephemeral routing token; the proxy looks the token up, swaps it for the real upstream credential, and forwards the body bytes unchanged. Enforces "agent X may call provider Y" at the credential boundary.

Adapters
AnthropicAdapter (oauth | api-key) · OpenAICompatAdapter (bearer | none)
Backends
Anthropic (HTTPS) · LM Studio (bearer) · Ollama (none)
Token mint
per turn, evicted at turn end

channels src/modules/channels/

host

A channel is a routing prefix bound to an authentication policy. ChannelRegistry holds the valid set (today: just cli); ChatServer is the bus↔WebSocket bridge that lets the CLI (and future Telegram, Slack, voice gateways) speak to and through the mail substrate.

Protocol
register · publish · mail · event · error
Outbound
channel.cli.out events route back to the right WS client

container src/container/

host

A `ContainerRunner` interface (spawn one turn, pipe stdin, collect JSONL, capture stderr/exit) with a DockerRunner production impl and a FakeRunner for tests. The daemon never talks to Docker directly — everything goes through the seam, which makes turn processing fully testable without a real Docker daemon.

db src/db/

host

SQLite, in-process, WAL mode. All writes happen in the daemon; CLI commands are readers. Schema is owned by numbered migration files under migrations/. Two repositories: AgentRepo and MessageRepo. The container never touches the DB.

bus src/bus/

host · in-process

Typed in-process EventBus. Emits notifications, not payloads — bodies live in the DB and subscribers fetch by ID. Not durable; crashes drop events. The DB covers durability for anything that needs it.

cli src/cli/

host · short-lived

The teamroom binary. Six subcommands; each one parses argv and delegates to a service function. chat holds a WebSocket open for interactive use; serve is the only one that runs the daemon in-process. Other commands discover the daemon's ports via the data/ports/ file convention.

Commands
serve · chat · send · inbox · thread · status

agent-config + agent-spec src/agent-config/ · src/agent-spec/

host

loadAgentConfig reads each agents/<name>/ folder at daemon boot — the agent.yaml, AGENTS.md, store/ — and validates required fields (name, provider, model, image_tag). buildSpec turns that config plus runtime context into the docker-run argv: image, mounts (/AGENTS.md, /store, optional /codebase), env, network.

A turn, end to end

What happens between "you type a message" and "the agent replies."

One trip through the system from a human in the CLI to an agent reply, assuming a LangGraph-backed agent talking to LM Studio. The Anthropic path is shorter — the SDK handles the tool-loop internally — but the mail/dispatcher/session/proxy pieces are all the same.

Figure 2. The same lifecycle drives every turn — agent-to-human, agent-to-agent, agent-to-list — because everything goes through MailDispatcher.sendMail(). Adding a Telegram channel is a new ChannelRegistry entry plus a separate gateway process; nothing below ChatServer cares.

Module dependencies

The compose graph (acyclic by construction).

startDaemon instantiates eight modules in this order. The integration test harness composes six of them with test-friendly substitutions and skips two that don't make sense in tests (observability needs a controllable clock; model-proxy isn't exercised by FakeRunner-based tests). Composition parity between test and prod is structural, not aspirational.

Figure 3. Direction is "depends on." No cycles. The channels → mcp-mail edge is the notable one: it forces inbound CLI chat to go through the same dispatcher entry point as agent-originated mail, which is what makes the substrate uniform.

Runtime & configuration

What the running system actually looks like.

One long-running daemon per host (started by teamroom serve) and one container per agent, kept warm across turns and torn down on idle. Channel gateways (the CLI today; future Telegram, Slack) are separate short-lived processes that connect to the daemon's WebSockets.

Milestone timeline

Six milestones in five days, then a deliberate cool-down.

Each milestone established something load-bearing and then froze it into an as-built. The cadence was unusually fast because each ship was deliberately narrow — see docs/retros/ for the per-milestone reflection on what worked and what bit.

Figure 4. The original M1-context milestone numbering changed during execution: M3 sharpened the "team substrate" thesis into "agent mail on an event-bus backbone" — which made mail (M4) the obvious next foundation. Memory and scheduling slid right because they want the communication substrate underneath them, not next to them.

Notable shape changes since the original plan

  • M3 narrowed. The original "team substrate" milestone fanned out into too many subsystems; it shipped narrowed, with mail as a separate thicker M4.
  • M4.5 inserted. The mail substrate from M4 exposed an inconsistency between test composition and prod composition; M4.5 was the "fix the harness so this can never recur" milestone, plus the channel-architecture refactor and the MCP-SDK retrofit.
  • M5 confirmed the direction. The LangGraph runtime is now the shape for non-Anthropic workers, not a future direction. The two-worker shape (Anthropic + LangGraph) replaces the single-runtime placeholder from M1.
  • M6 added (multi-harness). Originally implicit; promoted to a milestone once DeepAgents and Hermes appeared as concrete external harnesses worth integrating.

Capabilities today

What works now, what's deliberately deferred.

The honest snapshot. Things on the right are not "broken" — most are backlog items with explicit triggers (a concrete need that hasn't arrived yet). The roadmap's ## Backlog section has the full, current list with triggers.

Can do today

  • Run two agents (studio-assistant on LM Studio, claude-assistant on Anthropic) concurrently against the same daemon.
  • Send a CLI message to an agent via chat, get a reply, and continue the thread interactively.
  • Have agents send mail to each other (mail.send, mail.reply, cc, threading).
  • Read, write, edit, list, and search files under /codebase and /store from the LangGraph agent (via in-container filesystem MCP child).
  • Persist Claude session resume state across container turns (Anthropic worker, sidecar in /store).
  • Hold bounded conversation context across wakes within a container (LangGraph worker, cap 40, trimmed at HumanMessage boundaries).
  • Route every model call through the credential proxy — containers never see real API keys.
  • Inspect the daemon: PID + ports via teamroom status, inbox via teamroom inbox, threads via teamroom thread.
  • Mailing-list infrastructure exists (list:<name> addressing, registry, trigger listener) and is wired end-to-end mechanically.
  • Run the integration harness with composition parity to production (no mocks; real in-memory implementations of every effectful dep).

Deferred / known limits

  • Shell, git, ripgrep tooling — M5.1, immediately next. Filesystem MCP gives filename search but not content grep.
  • Per-agent memory — M7. Until then, "memory" means "the bounded message array inside one container's lifetime."
  • Scheduling / cron — M8.
  • Evals framework — M9. Today: unit + manual acceptance only.
  • Self-learning + ceremonies — M10.
  • Second channel (Telegram, Slack, voice) — deferred until a concrete need; CLI is the only channel today.
  • Mailing-list publishers — registry works but list:harness-activity is silent because turn-event publication isn't wired.
  • Durable event bus — current bus is in-process and ephemeral; crashes drop events. Mail bodies are durable (DB).
  • Streaming model responses — proxy buffers full responses to extract usage. SSE pipe deferred.
  • Session reattach on daemon restart — restart kills live containers; mid-turn state is lost (mail content preserved).
  • Mail attachments / structured payloads — body-only TEXT today. JSON blobs and file refs deferred.
  • Per-agent container idle tuning — single global default (30 min); per-agent override deferred.
  • Multi-model per agent — agents declare one model in agent.yaml; per-request selection deferred until a concrete need.
  • Live-model E2E test — manual acceptance only; the fix is real evals (M9).
