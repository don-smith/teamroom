Key boundaries:
  • The daemon owns lifecycle, mail dispatch, and the model proxy — everything agents need to exist and communicate.
  • Containers are opaque to the daemon beyond stdin wake envelopes. Each container hosts one runtime.
  • Model proxy is the single egress point for model calls — tokens are minted per-container-spawn, never shared.
  • Event bus decouples producers (dispatcher) from consumers (session manager, logging, channels).

Two-runtime strategy (post-M6 consolidation):
  • DeepAgents — for personas needing filesystem exploration, codebase reasoning, and persistent lifecycle (Archie the architect). Python, vendored at vendor/deepagents/.
  • Pi — for coding/CLI-oriented agents. TypeScript, uses the Claude Agent SDK via the @earendil-works/pi-coding-agent npm package.
  • Both runtimes share the same provider (OpenRouter), mail-MCP surface, and daemon-managed lifecycle.

4. Mail & Wake Protocol

sequenceDiagram actor H as Human (CLI) participant D as MailDispatcher participant B as EventBus participant S as SessionManager participant C as Container (stdin) participant R as Agent Runtime participant M as Mail MCP H->>D: teamroom send archie "Is this pattern right?" D->>D: Validate recipients, expand lists D->>D: Enforce thread cap D->>B: publish mail.delivered
{to, messageId, threadId, from, replyExpected: true} D-->>H: thread created B->>S: mail.delivered event S->>S: Dedupe by messageId S->>C: writeEnvelope({type: "wake", events: [...]}) C->>R: handle_wake(envelope) R->>R: Build wake prompt
(replyExpected shapes instruction) R->>M: mail.get(messageId) — read the mail M-->>R: message body R->>R: Read codebase files R->>M: mail.reply(messageId, body) — reply in-thread M-->>R: reply sent Note over R: replyExpected: true → must reply
replyExpected: false → silent unless value-add
Protocol guarantees:
  • replyExpected: true for direct CLI→agent and agent→agent mail. false for list fanout/cc.
  • Final assistant text is diagnostic only — Team Room-visible communication flows exclusively through mail tools.
  • Archie has an Archie-only fallback: if a reply-required wake ends without a successful mail_reply, the shim sends the final text via direct MCP. Telemetry fires so the failure is not hidden.
  • Wake deduplication by messageId prevents double-processing on container respawn.

Validation at daemon boot:
  • validateRuntimeProvider gates every runtime/provider combination — invalid pairs fail at config load, not inside the container.
  • deepagents runtime requires TEAMROOM_CODEBASE_PATH — the daemon fails loudly if the codebase is missing.
  • Provider tokens (LM Studio, OpenAI, OpenRouter) are only required when a configured agent uses that provider.

Startup ordering is load-bearing:
  • Ingress surfaces (channels, mail-MCP) start after their dependencies (model proxy, storage) and stop before them.
  • One persistent agent failing boot-spawn does not block daemon startup — the error is logged and startup continues.
  • Stop order reverses: channels → mail → mail-MCP → model proxy → storage.

7. Key Decisions

Decision Why
Runtime ≠ Provider Container loop (runtime) is separate from model routing (provider). Enables DeepAgents+OpenRouter and Pi+OpenRouter without coupling.
Daemon-managed respawn No Docker --restart. The daemon owns stdin, observability, and respawn policy — Docker is an opaque executor.
Lazy MCP discovery Docker "Up" means the process started, not "ready for wakes." First-wake latency pays the MCP+model cost; keeps boot liveness independent of dependencies.
replyExpected protocol Agents must not spam every wake but must not drop direct requests. Protocol-level distinction between must-reply and optional-silence.
Archie-only fallback If a reply-required wake produces no mail_reply, Archie sends final text directly. Loud telemetry so the underlying tool-call failure is not hidden. At N=2 this is correct; promote to a generic runtime contract when a second deepagents agent joins.
Skills as npm packages No repo-local skill tree. Skills consumed from @juicesharp/rpiv-pi, @locksmithdon/dons-flow — shared, versioned, multi-model.
