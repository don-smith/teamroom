## What shipped

Milestone 1 — "One agent that works." A single hand-configured agent (`assistant`) runs in a fresh Docker container per turn, called from a terminal CLI. End-to-end smoke test passed against a local LM Studio instance running `qwen/qwen3.5-9b`. Full unit + integration suite: 68/68 passing.

The 28-task implementation plan was executed via subagent-driven development: one to five subagents per task (implementer + spec-compliance reviewer + code-quality reviewer, batched where appropriate). 33 commits on the `single-agent` branch from plan-landed (`2ceeff8`) to M1-close. No task blocked on external help; no rework rounds needed beyond in-flight drift fixes.

Exit criteria from the spec met:

- Message sent via `teamroom send` → processed by the hand-configured agent in a fresh Docker container → reply visible via `teamroom tail`.
- No agent onboarding tooling; first agent hand-crafted.
- Structured JSON logs with trace IDs flowing CLI → daemon → container → reply.
- Daemon can be killed at any point; reconcile pass handles orphans deterministically.
- Every effectful dependency behind an interface; no mocking libraries anywhere.

One adaptation from the spec as written: the planned path used the Anthropic API with an `ANTHROPIC_API_KEY`, but during smoke-test prep we pivoted to an OpenAI-compatible local model (LM Studio) and renamed the downstream-milestone "credential proxy" to "model proxy / model abstraction layer." M2 will generalise the abstraction to multiple backends including Anthropic.

## 1. Keep doing

**Brainstorm → spec → plan → execute discipline.** Each stage produced a real artifact the next stage could ground itself in. When design questions surfaced mid-implementation (`/store` mount path, CLAUDE.md vs AGENTS.md, session-id semantics), the spec was the anchor we amended against, not something we drifted away from.

**Epiphany tabling to `docs/tabled.md`.** Every drift, concern, and "we'll come back to that" moment landed in `tabled.md` with enough context to reconstruct later. By retro time we had a single processed list rather than a dozen scattered half-memories. This practice is the single highest-leverage part of ways-of-working for a long milestone.

**Memory capture during brainstorm.** Three feedback-type memories were written during the M1 brainstorming session (`minimize-process-deps`, `see-only-as-far-as-needed`, `coupling-and-extensibility`, `testability-and-di`, `meta-consistency`) plus one project memory (`langgraph-direction`). Every one of them was invoked during execution to break ties on design questions. Future sessions will orient an order of magnitude faster.

**DI-first architecture with in-memory real implementations for tests.** The "unit vs integration" line dissolved because `SQLite :memory:` + `InMemoryBus` + `FakeRunner` run at unit-test speed. Whole suite completes in ~1.5s. Zero mocking-library calls. When the Anthropic → OpenAI SDK pivot landed, the `LlmClient` seam absorbed it in minutes.

**Subagent-driven development with batched implementer + combined review.** The pivot from strict-per-task review to batched implementer + single review pass per batch (user's "option B" mid-execution) dropped roughly two-thirds of the subagent dispatches without degrading quality. The reviews still caught real defects (e.g., the `@types/node` drift on Task 1; plan bugs in FileNotifyBus and buildDockerRunArgs in later batches). Complexity-matched review cadence > blanket protocol.

**"Nothing silent, nothing inconsistent, nothing crashes" as a design principle.** Quoted literally in subagent prompts for daemon-core tasks. Each task shipped with global safety nets and reconcile-on-startup logic that make the system well-behaved under crash scenarios.

**NanoClaw as a reference when stuck.** The subscription-auth dead end would have cost significant design time except that NanoClaw had the same problem and an answer. The "look at the sibling project" move is worth preserving.

**Co-located tests** (adopted late but decisively). After the move, any module's source + tests are one directory read away. Refactors stay local. This is the test layout going forward.

**The `## Related` README convention.** Established mid-M1, applied to every multi-file module. Turns the repo into a navigable knowledge graph rather than a folder tree; any module is ~2 link hops from any other via its README.

## 2. Stop or change

**Flag test layout (and config, and deployment assets) DURING design or plan review, not during execution.** The test-layout drift went uncaught until Task 28 despite being visible in the plan all along. Config/secrets wasn't discussed in brainstorming at all and cost us a round of reconsideration during smoke-test setup. SQL migration assets weren't considered in the build step and only surfaced at `docker build`. These are plan-level concerns that need a dedicated review lens.

**Mentally dry-run the plan's code before committing the plan.** M1 surfaced at least seven plan drifts (FileNotifyBus chokidar ready race, FileNotifyBus close-doesn't-wake-resolvers, FileNotifyBus namespace type import, buildDockerRunArgs env-sort test inconsistency, parseEvent spread ordering, processTurn genId collision, Anthropic SDK TextBlock type narrowing, `.gitignore` `.gitkeep` exception), all of which a careful mental execution of each test/impl pair would have caught. Implementer subagents caught them in practice, but that's a fallback, not a plan-review discipline.

**Don't default to "strict per-task review" as a blanket protocol.** The strict protocol was appropriate for the turn-processor (real logic, high risk) but wasteful for safety-nets (10 lines of global handlers, no tests). Starting with strict and then negotiating a relaxation mid-execution was the right outcome, but the right STARTING shape is: review cadence follows task complexity, not position in a sequence. Add a `## Review Approach` section to the plan template per-task so the default is explicit.

**Update READMEs + root docs at the same moment as the code that invalidates them.** Both the root `README.md` and `agent-runtime/README.md` drifted to reference Anthropic after the LM Studio pivot. We caught it in the README-convention pass but it should have been caught at pivot time. Principle: doc updates are part of the change that invalidates them, not a follow-up.

**Don't assume runtime / build asset concerns are resolved because unit tests pass.** The SQL migrations didn't land in `dist/` because `tsc` doesn't copy non-TS files. Unit tests (running `.ts` directly) never saw the bug. Need a production-build sanity check earlier — probably at task-plan time, by explicitly listing what runtime assets need to exist and how they get there.

**Be explicit about what "mocking" means when specifying DI.** One reviewer check flagged that test implementations are genuinely real in-memory code (InMemoryBus uses real EventEmitter-like logic; `:memory:` SQLite is real SQLite). Future-Claude shouldn't be tempted to reach for `vi.mock` even when a task looks trivial enough to "just stub."

**Scope creep from user-initiated questions.** The "can we use my subscription?" question was correctly explored but shouldn't have been handled in the same session as the smoke-test phase. Better pattern: table design-impact questions to a scoped follow-up, keep the current phase's work linear. (We did eventually — Option D / LM Studio — but with more thrash than ideal.)

## 4. Commit to memory

**Update: `feedback_teamroom_testability_and_di.md`** — append a paragraph: co-located tests (`src/<module>/<file>.test.ts`) are the canonical layout; reserve `tests/integration/` only for cross-module tests.

**New: `feedback_teamroom_plan_preexec_review.md`** — before approving any implementation plan for execution, both Claude and the user dry-run each test/impl pair mentally, check for plan-level gaps (config/secrets handling, test layout, deployment-asset flows, cross-task identifier consistency), and explicitly confirm the plan is complete. The M1 experience: ≥7 drifts a careful pre-execution read would have caught; the user self-identified missing this review as the root cause of one of those drifts (test layout).

**No new project memories.** The state of M1 is in the codebase and the (soon-to-be-amended) spec; no facts need to survive in the cross-conversation memory that aren't already in the repo.
