# M4.5 Retro — AI-Native Harness

*Date: 2026-04-22. Frozen at commit. Future amendments go into a new retro.*

> **Historical note (2026-06-13):** The project no longer maintains a repo-local `.agents/skills/` tree. Skills are now imported as npm workflow packages. References to `.agents/skills/` in this retro describe the M4.5 practice at the time and should not be treated as current instructions.

## 1. Keep doing

- **Scoping before brainstorming.** Asked for a "scope list" first; only then opened the design space. Caught two architectural reframes (channel-as-architecture; tabled.md as single working-memory location) that would have been harder to land mid-implementation.
- **Pause when architectural smells surface mid-brainstorm.** Distinct from pre-work scoping: this is the willingness to *reshape* the milestone when investigating a smell reveals a deeper, more valuable change. The CLI work was originally a polish-the-CLI milestone; recognizing that the CLI plumbing was wedged into the wrong places (DB-direct, `/cli/send` on mail-MCP, `tail` watching FileNotifyBus) turned it into a fundamental architectural shift. The milestone shipped both deeper and more useful for it.
- **Mindful scope management.** Things that should slot in (the env-file unification surfaced during acceptance; the followups→tabled consolidation; the post-acceptance UX fixes for `chat`) landed inside M4.5 because they were small, tightly motivated, and complete the milestone's intent. Things that shouldn't (the cap-warning feature, second-channel work, lists end-to-end verification) stayed out. The judgment held — nothing snuck in; nothing ducked accountability.
- **Brainstorm with explicit options + recommendation per question.** Each design question got 2-3 framed options + a recommendation + a "push back if I'm framing this wrong." User push-back twice reshaped the milestone (channel architecture, daemon.stop ordering); the format made the push-back surgical.
- **Subagent-driven execution with two-stage review.** 24 groups, ~24 implementer + spec + code-review cycles. Reviews caught real issues every group (inputs to fix; not noise). The pattern scaled to a 38-task plan without losing rigor.
- **Bundle related tasks for review optimization.** User asked early: "let's bundle to optimize review cycles." Reduced 38 plan tasks → 24 dispatched groups; reviewer dispatches dropped ~37%. Quality didn't suffer because each bundle was thematically tight.
- **Combined spec+code review for small, well-patterned groups.** Once a pattern was established (e.g., compose-modules), one combined-review subagent dispatch replaced two. Saved a round-trip per group from Group 15 onward.
- **Reviewer-driven inline follow-ups.** Important issues from each group review got fixed in a follow-up commit *immediately*, not deferred. Kept the per-group state clean and the as-built honest.
- **Real-implementation tests (no mocks).** Every new module's tests use real `composeStorage(:memory:)`, real `EventBus`, real `WebSocket` clients. Caught actual integration issues (e.g., dispatcher event payload shape) that mocks would have hidden.
- **Composition parity by construction.** §15b goal delivered structurally — `startDaemon` and `composeIntegrationHarness` call the same six modules. The M4 drift bug class can't recur.
- **Verify implementer-reported "pre-existing" failures.** Twice (Groups 4 and 18) the lm-studio-real test was reported as a "pre-existing failure" or "transient unrelated to this work." Verified directly both times — both were transients that resolved on the next full-suite run. The `no_failing_tests` memory rule worked exactly as designed.
- **Evolve ways-of-working *during* the milestone, not just at retro.** The followups→tabled unification happened mid-close-out when the practice friction surfaced; landed in `ways-of-working.md` and the `epiphany-tabling` skill before the retro was written.

## 2. Stop or change

- **Milestone size — too big for a "point five."**
  Pain: M4.5 hit the Claude Code max session limit two-to-three times during planning + execution. The full work (61 commits, ~6700 line diff, 24 task groups) is the largest single milestone shipped to date — bigger than any of the named M1/M2/M3/M4 deliveries. A point-five is supposed to be a smaller intermediate beat, not a larger one.
  Change: target one milestone per max session as the planning unit. When a brainstorm reveals scope larger than that, decompose into multiple milestones during planning (not during execution). The next milestone (LangGraph studio-assistant + multi-agent-family runtime) is already known to be substantial; right-size it during scoping rather than assume it'll fit.

- **No mechanism to sustainably extend `superpowers` skills.**
  Pain: we landed a half-dozen process improvements during M4.5 (verify transient-failure claims; bundle tasks; combined reviews; inline follow-up commits; bundling-pass step in plan-writing). All of them want to live as augmentations to existing `superpowers` skills (`subagent-driven-development`, `writing-plans`, etc.). Today the options are: edit the upstream skill (forks it, loses upstream updates), or capture in retro action items (drift back to forgotten advice). Neither is durable.
  Change: investigate a skill-augmentation pattern — a project-local layer that sits *on top of* the upstream superpowers skill rather than replacing it. Could be: a project-side companion file the skill loads as additional context, or a wrapper skill that invokes the upstream + appends, or a hook in the `.agents/skills/` discovery path. Action item below to explore options.

- **Bisect hazard from retroactive helper extraction (Group 17).**
  Pain: commits `11c7023` and `81605da` import from `./query-client.js` which doesn't land until commit `5854239`. The intermediate commits don't compile in isolation; `git bisect run tsc` would false-positive across them. Branch-end state is correct, but a future bisect could be fooled.
  Change: when a subagent extracts a shared helper after writing two near-identical files, the extraction must either land in commit 1 (no commit-1 in isolation) OR be deferred to a separate group with the original commits self-contained. Add this guidance to the implementer prompt template (a one-line "if you extract a shared helper, ensure each commit compiles in isolation").

- **Build-state drift caught the user mid-acceptance.**
  Pain: user couldn't see my CLI/observability changes — `dist/` hadn't been rebuilt after commits, and `teamroom` symlinks to `dist/cli/main.js`. Cost time during acceptance.
  Change: either (a) rebuild after every meaningful change in the worktree, (b) add a `prepublishOnly`/`postinstall` style script that surfaces stale `dist/`, or (c) document the rebuild dance more loudly in `src/cli/README.md`. (a) is heavy, (b) is medium effort, (c) is one line — start with (c), promote later if it bites again. Action item below.

- **Subagent context limits twice cut work mid-task.**
  Pain: Groups 9 and 20 hit usage limits before the implementer could report. Both times the work landed (commits visible) but no report came back; required controller-side verification.
  Change: for any group with significant scope or multiple files, bias toward smaller bundles. The "combined review" optimization is good; "bundle 4 cleanups into one subagent" is a stretch when each cleanup involves multi-file edits.

- **Plan-vs-reality drift on bus-event payloads (Group 13).**
  Pain: plan sketched `ChatServer` subscribing to `mail.delivered` for channel routing; dispatcher actually publishes `channel.cli.out` for channel recipients (`mail.delivered` is agent-only). Implementer caught this and pivoted, but the plan was wrong.
  Change: when writing a plan that depends on a publish/subscribe shape, grep the publisher to verify the event name + payload before drafting the subscriber. Pattern is general: read the producer before specifying the consumer.

- **Spec → plan → code drift on the migration approach.**
  Pain: spec described migration 004 as TS-extended migrator; plan corrected to plain SQL with SQLite JSON1; code matched the plan. The deviation was flagged inline, but the spec was technically wrong at user-approval time.
  Change: when a spec assertion is overcautious or speculative ("this requires X infrastructure change"), flag it as a check-before-implementing item rather than locking in the assertion. The plan-writing phase is where these get cross-checked; build that into the plan-writing workflow.

- **`MailMcpServerOpts` → `MailMcpServerDeps` rename was incidental, not intentional.**
  Pain: SDK retrofit (Group 8) silently renamed the deps interface, breaking convention with sibling code (`MailDispatcherOpts` etc.). No external consumer broke; just inconsistency.
  Change: subagent prompts for refactor work should explicitly forbid silent renames. "If you rename a public-facing interface, surface the rename in your report and explain why."

## 3. Promote to artifact

- **"Bundle bite-sized tasks for review optimization."** Sighted: M4 (user mentioned the pattern in passing) + M4.5 (user formalized: "let's bundle to optimize review cycles"). Two prior sightings = promote per the rule. Candidate: extend the `writing-plans` skill (or the `subagent-driven-development` skill) with an explicit "bundling" step — after writing the plan, propose a bundling pass that groups same-shape, same-review-surface tasks into groups before execution.

- **"Verify implementer claims about transient test failures before accepting them."** Sighted: M4.5 Group 4 (lm-studio-real flake), M4.5 Group 18 (same test, same misframing). Two prior sightings. Candidate: addition to `subagent-driven-development` (or a tightening of the existing `feedback_teamroom_no_failing_tests` memory rule) — "when a subagent reports a failure as pre-existing/environmental/transient, the controller MUST verify via `npm test` before accepting."

- **"Inline follow-up commits per review, not at the end."** Sighted: every group of M4.5. Pattern: when a reviewer flags Important items, fix immediately in a follow-up commit before moving to the next group; don't accumulate a "review backlog." Candidate: addition to `subagent-driven-development` describing the inline-fix discipline.

- **"Combined spec+code review for small/well-patterned groups."** Sighted: M4.5 Groups 15 onward. Candidate: one-line note in `subagent-driven-development` — once a pattern is well-established across multiple groups, the spec and code reviews can be combined into one subagent dispatch to save a round-trip.

- **"Closing-a-milestone" workflow as its own skill candidate.** Sighted: M3, M4, and M4.5 closes all involved the same broad sequence — process tabled.md → consolidate to roadmap Backlog → write as-built → purge spec+plan → write retro → update roadmap milestone status. The mechanics live across `epiphany-tabling` (processing), `writing-as-built` (purge), `writing-retros` (retro), and ad-hoc roadmap edits. M4.5 close exposed the full sequence as a discrete ritual. Candidate: a project-local `closing-a-milestone` skill (or runbook) that bundles the steps + acts as the entry point. Better than re-deriving the sequence each milestone close.

(`tabled.md` unification + roadmap Backlog consolidation are not in this section because they were promoted *during* the milestone, not deferred to it.)
