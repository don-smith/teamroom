The size discipline from the M4.5 retro paid on its first application. (M4.5's own advice — the M4.5 retro's §2 "milestone size" — worked exactly as intended.)

Plan prescribed Strategy A ("bundle Tasks 6–11 into one commit"); the implementer followed it; intermediate state never broke bisect. M4.5 retro's §2 "bisect hazard" point got concrete reinforcement.
- **Inline follow-up commits per review — zero review backlog.** Every Important item from spec or code review got fixed in its own commit before the next group dispatched. Six inline-fix commits land in the log: `7774cf9` (tighten registers-both test), `c3119e9` (trim at HumanMessage boundary + drop cast), `261b809` (unreadOnly naming), `244de15` (FS root filter), `7fb45d7` (drop `as never` + boot prefix), `73fead7` (recursion-limit bump post-acceptance). Log reads as a sequence of review-driven improvements.

- **Tight implementer-prompt scoping with verified facts up front.** For the Group D+E dispatch and the Task 18 dispatch, I pre-read files, verified signatures in `node_modules/*.d.ts`, and handed over a self-contained brief with the exact shapes. Subagents didn't need to re-discover the world. Group D+E (the largest dispatch) landed cleanly despite being a six-task bundle.
- **Used research subagents before scope commitments.** Twice the user's scope question ("can we do filesystem tools inline?") triggered a research dispatch to actually read LangChain/MCP docs before I recommended. The first research I did alone was too shallow and the user pushed back — the second pass was dispatched properly, corrected my over-conservative scope estimate, and identified the drop-in path.
- **Reviewer pushback shaped architecture, not just polish.** The `slice(-40)` trim was working code and all tests passed. Code review flagged it as a real correctness risk (ToolMessage orphaning). Fix added a boundary-walk algorithm + a new test that scripts tool-call round trips — the test exists now because the reviewer earned it. Same pattern with `as never` cast, `onError` overloading for warnings, and the FS-root-missing crash.
- **Acceptance-driven tuning, not plan-time locking.** `RECURSION_LIMIT = 10` from the plan made it through code review (because it was internally consistent) but failed during user acceptance with a small model. Swapped to 50 as a targeted post-acceptance fix with its own commit (`73fead7`) and full explanation in the constant's JSDoc. Plan-time constants that survive implementation don't automatically survive acceptance — stay willing to retune.
- **User-prompted scope reshape was cleanly integrated.** Filesystem capability was raised by the user *after* the original 17 tasks landed. We didn't panic, didn't redo the plan; we scoped two additional tasks (18 + 19) with their own bundle pattern, inline-fixed Important review items, and closed them before retro. The sub-milestone-within-milestone pattern worked.
- **Model swap mid-acceptance instead of shipping flaky.** Gemma-4-e4b was spec'd, shipped, and failed acceptance. Rather than document "works but flaky with this model," we swapped to GPT-OSS-20b and reran — clean success. The architecture didn't need apologies; the model did.
- **Evolve ways-of-working in-flight.** User caught the retro-ordering backwards mid-closeout; we fixed `docs/ways-of-working.md` before moving on to the as-built. Second milestone in a row the ways-of-working doc got edited *during* closeout rather than after — that's now a pattern, not an incident.

## 2. Stop or change

- **Research before scope-committing — the only real hiccup this milestone.**
  Pain: when the user raised filesystem access, I proposed a scope estimate (6 hand-rolled tools → M5.1 mini-milestone) based on a shallow memory-driven read of the LangChain ecosystem. User pushed back — "are you sure you did enough research?" — and a proper research-subagent dispatch revealed the drop-in path (`@modelcontextprotocol/server-filesystem` over MCP stdio, which is literally the LangChain team's own tutorial pattern). The corrected scope was half the size and kept the work in-milestone. Zero cost to the milestone because the push-back caught it; real cost had the user trusted my first scope.
  Change: when estimating scope for a new library or integration, default to dispatching a research subagent first rather than scope-guessing from memory. Treat memory-driven scope estimates as "probable floor" not "probable final." A companion observation: when a research subagent's finding contradicts observed runtime (the MCP-prefix confusion later in the same milestone), investigate the contradiction rather than picking a side — existing green tests are ground truth.

- **Plan-time numeric constants need provenance annotations.**
  Pain: `RECURSION_LIMIT = 10` in the plan looked like a decided value. It wasn't — a first-guess with no basis in LangGraph docs or prior experience. User acceptance exposed it mid-flow (echoed WAKE_PROMPT, confused debug cycle). The fix was one line; the diagnostic detour wasn't.
  Change: `writing-plans` skill should require each numeric constant in a plan to carry provenance: library default, prior-milestone value, measured value, or "first-guess — tune during acceptance." Reader then knows which are load-bearing and which are tentative.

## 3. Promote to artifact

- **"Onboarding a new agent to Team Room" as a runbook (or skill).** First sighting *as a visible pattern*. M5 is the first time we're connecting a fundamentally different agent shape (LangGraph-backed, local model, in-container MCP filesystem) to the same substrate. M6 already commits to two more (DeepAgents, Hermes). The roadmap's seven personas (Archie, Pam, Dev, Desi, Doc, Eve, Hisa) each imply further onboardings. Each onboarding involves: defining the agent's role + persona, wiring the harness to the message bus, selecting the model, declaring tool surface, tuning prompts, iterating on reliability, writing AGENTS.md-equivalent. Codifying this as a reusable runbook (or a skill that walks through it) means the next agent lands in hours, not a fresh design session. The LangGraph agent itself is only partially onboarded — it has no role, no evals, no characterization — so the runbook is also what will tell us when an agent is "ready" vs. "still being onboarded."

- **"Deferred-green bundle-commit for cross-cutting refactors."** Sighted: M4.5 retro §2 "bisect hazard" (the original); M5 Group D+E (the plan explicitly prescribed Strategy A bundle-commit and it worked). Two prior sightings. Candidate: addition to `writing-plans` skill — "if a group of tasks cannot typecheck green at every intermediate commit, either (a) bundle them into one commit or (b) land the intermediate files as stubs that compile. Call the choice explicitly in the plan."

- **"In-milestone scope extension when user surfaces new requirements."** Sighted: M4.5 retro §1 "Mindful scope management" (env-file unification, followups consolidation landed mid-milestone); M5 Tasks 18 + 19 (filesystem capability added after core plan landed). Two prior sightings. Candidate: short addition to `docs/ways-of-working.md` — "A mid-milestone scope addition is in-bounds if it's small, tightly motivated, and completes the milestone's intent. A re-scoping conversation is in-bounds if a discovered requirement is structurally required for acceptance. A new unrelated feature request is a separate milestone."

- **`closing-a-milestone` as a named skill (or runbook).** Sighted: M4.5 retro §3 (candidate), and M5 close (the sequence — process tabled → as-built → purge spec+plan → update roadmap → retro — ran identically). Two prior sightings. The skill doesn't exist yet; M4.5 action item #7 was to "decide" whether to build it. M5 close is the second sighting. **Decision candidate: build it now, before M5.1.** Each close runs the same ~6 steps, and codifying the sequence as an entry-point skill would save the controller from re-deriving it each time.

- **Small-model-pseudo-code-tool-calls as a documented failure mode.** First sighting (this milestone's acceptance). Specific pattern: an OpenAI-compat-served small model emits things like `myFunction('mail_list', {'unreadOnly': true})` or `ereseq:mail_list{unreadOnly:true}<tool_call|>` in message *content* instead of as proper `tool_calls` fields on the AIMessage. The model "knows" tool calling exists but can't execute the OpenAI function-calling protocol faithfully. One sighting; candidate for a §4 memory entry so future-us recognizes it fast without re-diagnosing.

## 4. Commit to memory

- **Add `feedback_teamroom_harness_contract_definitiveness.md`** — as agent-harness diversity grows (Claude Code, LangGraph, DeepAgents, Hermes, future), the connective tissue between Team Room and an agent is the load-bearing surface that determines whether new harnesses can actually plug in. The contract today spans: container mounts (`/AGENTS.md`, `/store`, `/codebase`), env-injected config (`TEAMROOM_MODEL`, `TEAMROOM_PROVIDER`, `TEAMROOM_MODEL_BASE_URL/API_TOKEN`, `TEAMROOM_MCP_URL/TOKEN`), stdin wake envelopes, a stdout-is-reserved convention, MCP tool discovery over HTTP/stdio. Each new harness tests whether this set is definitive enough. The memory entry is the standing instruction to treat this surface with extra care — document deviations, notice ambiguity, prefer clear contracts over convenient shortcuts. Triggered by: this milestone made the diversity real (second harness); M6 will triple the harness count.
- **Add `project_teamroom_small_model_tool_protocol_failure.md`** — a project memory entry capturing the small-model-pseudo-code-tool-calls failure mode (§3 above). The diagnostic cost a debug cycle this milestone; a named entry makes the recognition trivial next time.
- **Sharpen `feedback_teamroom_protocol_sdk_default.md`** — extend its framing to include library-provided *testing helpers* (like `fakeModel()`) alongside reference SDKs. One-line amendment: "when a library ships a fake / mock / testing helper for its own interfaces, default to using it instead of hand-rolling."
- **No other new memory entries.** `composition_parity`, `see_only_as_far_as_needed`, `minimize_process_deps`, `protocol_sdk_default`, `testability_and_di`, `no_failing_tests`, `flexibility_on_discovery`, `coupling_and_extensibility`, `meta_consistency` all earned their keep this milestone — they shaped real decisions. They stay as-is.
