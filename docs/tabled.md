# Tabled — working-memory scratch pad

This file is the single working-memory location for anything noticed mid-task that we don't want to chase right now: epiphanies, follow-up items, design questions, technical-debt observations, ideas for later. Add an entry as a short bullet with enough context to reconstruct cold; remove it once it's processed (acted on, rolled into another document, or consciously dropped).

Keep this file small. If it grows past a screen of content, that's a signal to process, not to let it sprawl.

**Format for each entry:** a one-line title, a 2–4 line description, and (when known) where its next destination probably is — `docs/roadmap.md#backlog` is the most common destination at milestone close for items still relevant; other destinations include spec, runbook, skill, memory, retro, or drop.

**Milestone-close processing:** at the end of each milestone, sweep this file. Outstanding items worth keeping roll into [`docs/roadmap.md#backlog`](roadmap.md#backlog); completed/obsolete items are dropped. The file ends each milestone empty (or near-empty).

Grouping here to address as one small polish pass once the milestone's implementation layer is further along (likely after F1 runbook consolidation lands):
  1. **Respawn counter never resets.** `respawnCounts` in `session-manager.ts` only grows within a daemon lifetime. Add a test that probes "agent stays dead after cap, subsequent recovery fails to restart" to lock in the target behavior (before or after the reset fix — that's the invariant we're naming).

Closes the silent-session-default risk window for future compose-layer callers. ~5 line touches in `setup()` test helpers (pass `lifecycleFor: () => "session"` explicitly in the non-persistent test suite).
  3. **Operator visibility when cap hits.** When an agent's respawn count reaches 10, the only signal is a JSON log line (`session.persistent_respawn_cap_reached`). No health endpoint, no admin mail, no daemon-side alert. Consider: (a) an admin mailing list + dispatcher-level notification, (b) enrich `teamroom status` to surface capped-dead agents, (c) a health endpoint summarizing per-agent state. Pick the lightest option once M6 Archie + Dev are wired and we see how visible the cap actually needs to be in practice.
