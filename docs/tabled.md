## Open entries

- **Runbook vs. skill boundary — working heuristic carried forward from M1 close.** Partial resolution landed in `.claude/skills/capturing-learnings/` and `docs/ways-of-working.md`: *skills are tactical how-tos (one specific thing), runbooks are broader processes or practices that often compose multiple skills, and both can invoke scripts.* This is a heuristic, not a rule — the next time we produce a runbook and a skill that share a boundary (most likely: the first agent-onboarding runbook in M2), revisit and decide whether the split still fits. Probable destination: refinement of the `capturing-learnings` skill text, or promotion of the pre-execution plan review from inline rhythm to its own skill.

- **Multi-model-per-agent and per-request (or per-conversation) model selection — deferred past M2.** User confirmed 2026-04-18 during M2 brainstorm: an agent will eventually have access to multiple models and choose per request, or at least per conversation (which spans multiple messages). Beyond per-call selection: agents will have *skills* and an *array of models* with instructions on which model to use for which type of work (e.g., cheap/fast model for triage, big model for synthesis). Out of scope for M2 (which proves credential injection + native-request translation against N=2 backends with one model per agent). M2's registry-value type and `agent.yaml` schema carry an inline comment noting the future list-shape. Probable destination: a future-milestone spec section once a concrete agent has a real reason to switch.

- **Streaming model responses — deferred past M2, revisit before "soon" feature work.** M2 keeps agent-runtime non-streaming (matches M1). Anthropic's native streaming is SSE; the proxy will need true SSE pipe + parse usage from terminal `message_stop` event. Probable destination: M3-or-M4 spec section once an agent surface-level needs realtime streaming (long completions, voice, etc.).

- **Tool-call telemetry as child spans of the turn trace — confirmed alignment, no action in M2.** The span-shaped log vocabulary established in M2 (`{event, traceId, spanId, parentSpanId, ...}`) is intended to extend to tool-call records (`tool.call.completed`) when agents start emitting them in M3+. No M2 work; capture here so the M3 design knows the pattern is already in place.

- **Two-way / streaming transport between container and proxy — defer evaluation until streaming forces the question.** Candidates: SSE (matches Anthropic's native streaming), HTTP/2 (multiplexing), WebSockets (probably overkill for this shape), tRPC (different abstraction layer). M2 stays on plain HTTP/1.1 keep-alive. Probable destination: included in the streaming spec when that lands.

- **Future agent runtimes beyond LangGraph — Claude Agent SDK (Node), subagent-spawning, etc.** User confirmed 2026-04-18 during M2 brainstorm: in addition to LangGraph, future agents may want the Claude Agent SDK for the full agent-loop + tool-call + subagent machinery. It's also easy to imagine some agents being responsible for spawning their own subagents (colleagues/teammates AND on-demand task-agents). Out of scope for M2 — but a constraint on the container contract: keep the host/container boundary thin enough that an agent's runtime can be Claude Agent SDK, LangGraph, or our own minimal shim, interchangeably. Probable destination: agent-runtime shape revisited when the second-runtime decision earns its second sighting.

- **Anthropic programmatic-subscription gates — fallback plan.** M2 plan is `@anthropic-ai/sdk` in the container (mode-agnostic, `apiKey = routing-token`) plus a server-to-server OAuth exchange in the proxy with temp-key caching across turns. Anthropic has been actively restricting programmatic use of subscription tokens outside Claude Code itself; if this trips the abstraction, fallback is the Claude Agent SDK (Node) inside the container, which they sanction (and which would itself perform the exchange). Watch for: 401/403 specifically on the proxy's exchange call, signed-request / device-attestation requirements that we can't reproduce. The proxy-side cache reduces exchange-call frequency from "every turn" to "every temp-key TTL," which substantially lowers detection risk but does not eliminate it. Probable destination: implementation-time decision; capture findings in the M2 as-built.

- **CLI bypassing the channel abstraction — refactor when channels land.** The `teamroom send` / `teamroom tail` CLI commands currently write directly to `MessageRepo` and subscribe directly to `NotifyBus`. Once channels become a first-class abstraction (M3 team-substrate or whenever the first non-CLI channel lands — Telegram, Slack, etc.), the terminal CLI should be a `Channel` impl like the others rather than a special-cased DB writer. M2 keeps the current shape (no point introducing channels just for the CLI). Probable destination: M3 spec section on channel abstraction.

- **M2 plan templates pre-specified code without grounding in source — surfaced 4 times in Phase 1 (Tasks 2–3).** Same root pattern, four sightings: (a) Task 2 test skeleton imported `afterEach` but didn't use it, omitting the `rmSync` cleanup convention used by every other `mkdtempSync` test in the codebase — code reviewer caught it as Important. (b) Task 2 plan listed `src/daemon/main.ts` as a "Modify" file, but `main.ts` didn't actually need any change (PID handling all lives in `daemon.ts`). (c) Task 3 plan asserted `parseEvent`'s buggy spread shape was `{ type, ...parsed }` in the `reply` branch — reality: `reply` had no spread; the bug was in `status`/`log` branches. The implementer's first-test-case (reply spoof) doesn't actually exercise the fix. (d) Task 3 plan template asserted `expect(evt).toBeUndefined()` for non-object/invalid JSON — actual `parseEvent` return type doesn't include `undefined`; it returns `{ type: "unknown", raw }`, so the plan's assertion would have been a TS compile error. Implementer subagents adapted in-flight in all four cases (the code-quality and spec reviews caught the rest). The pre-execution review (per `feedback_teamroom_plan_preexec_review`) is exactly the discipline that's supposed to catch this — root cause: the M2 plan was written without dry-running each test/impl pair against the actual current source. Probable destination: M2 retro action item to either (i) update the existing pre-execution-review feedback memory to specifically call out "test-skeleton assertions and pre-specified return-statement shapes" as high-risk drift surfaces, or (ii) promote the pre-execution review from inline rhythm to its own skill, given this is now the second milestone where unreviewed plan drifts surfaced — promotion threshold per the existing memory.
