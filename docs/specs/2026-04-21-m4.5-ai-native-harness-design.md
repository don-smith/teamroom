# M4.5 — AI-native harness, channel architecture, composition refactor

*Spec date: 2026-04-21. In-flight design for the active milestone. Will be purged into the as-built at milestone close.*

## Overview

Two intertwined threads:

1. **AI-native surface.** The harness becomes drivable from outside with low friction — chat with agents, inspect inboxes — so that scenarios we used to test by hand-tailing one terminal and hand-sending from another can be exercised by an AI collaborator (or a human) through clean, machine-friendly CLI commands.
2. **Architectural cleanup that the AI-native work surfaces.** The current CLI plumbing — direct DB writes, a `/cli/send` route bolted onto the mail-MCP server, a `tail` command backed by a second event bus — is a smell. Resolving it means establishing the **channel** as a first-class architectural concept, with CLI as the first concrete instance, and refactoring `startDaemon` from a 322-line procedural narrative into a thin top-level composer over named subsystem modules.

The §15b composition-parity work originally scheduled here is delivered **by construction** through the modules refactor (test harness and `startDaemon` call the same `compose*` functions; wiring shape can't drift), not by a snapshot test or a single shared builder.

## Scope

### In scope

- **Channel architecture.** Channel registry; CLI as the first concrete channel; address scheme `agent:* | list:* | channel:<name>:<id>`; data migration of existing `cli:*` rows.
- **Daemon-owned external surfaces (two WebSocket ports).**
  - `chat` WebSocket — bidirectional bus interaction; channel registration on connect.
  - `queries` WebSocket — read-only inbox/thread queries (request/response shape; could become read-write later).
- **CLI command rewrite** — WebSocket-based; `chat`, `inbox`, `thread`, `send` commands. Drops `tail`. Drops the DB-direct write path. Drops the mail-MCP `/cli/send` path.
- **Mail-MCP cleanup** — remove the `/cli/send` sibling endpoint; mail-MCP becomes pure MCP again.
- **§15a MCP SDK retrofit** — replace hand-rolled JSON-RPC over `node:http` with `@modelcontextprotocol/sdk` (`McpServer` + `StreamableHTTPServerTransport`); migrate the 15 server-side tests.
- **Composition refactor.** `src/modules/` with eight named modules and `compose*` factory functions. `startDaemon` and `composeIntegrationHarness` both call the same composers with different concrete deps.
- **Dead-code removal.** `Orchestrator`, `turn-processor`, `FileNotifyBus`, `reconcile`, `tail`, file-watch scaffolding, and the legacy CLI orchestration path that they support — all removable once the channel-based CLI replaces them.
- **Port-file convention.** `<dataDir>/ports/<surface>.port` for every daemon-opened HTTP/WebSocket port. Replaces the one-off `teamroom-mail.port`. Agent containers continue to receive the mail-MCP port via env var (cleaner for daemon-controlled processes); user-started CLI tools read the port files.
- **`buildSpec` extraction** — promote the 40-line inline closure in `startDaemon` to a real function with explicit deps. Lives at `src/agent-spec/build-spec.ts` (sibling to `agent-config/`).

### Out of scope (carved to followups)

- §16 turn event publication (`SessionTimerManager` publishing `turn.started` / `turn.completed`).
- List system end-to-end verification (lists work mechanically but haven't been exercised live).
- List addressing redesign (does `list` deserve a top-level prefix alongside `agent` and `channel`?).
- Mail-MCP / daemon coupling architectural review.

## Module list

Eight named modules under `src/modules/`. Each exposes a `compose<Module>(deps): Module` factory function and a `<Module>` interface for the things it returns.

| Module | Responsibility |
|---|---|
| **`storage`** | DB connection, migrations, repos (`AgentRepo`, `MessageRepo`, `TurnRepo`). Pure persistence. |
| **`observability`** | Clock, log sink, `JsonLinesLogger`. Future telemetry/tracing slots in here. |
| **`messaging`** | `EventBus`. Foundational pub/sub substrate. Small module; crisp boundary. |
| **`mcp-mail`** | `MailDispatcher` + `MailingListRegistry` + `MailingListTriggerListener` + `MailMcpTools` + `MailMcpServer`. The whole mail system: routing engine, list infrastructure, agent-facing MCP surface. |
| **`model-proxy`** | `TokenRegistry` + provider adapters + `LocalModelProxy`. |
| **`session-management`** | `DockerRunner` + `SessionTimerManager` + the three bus subscriptions (`mail.delivered`, `mail.sent`, `tool.call`). |
| **`channels`** | `ChannelRegistry` + chat WebSocket endpoint + per-channel registrations. Bus subscriptions for outbound channel-addressed mail. |
| **`queries`** | Read-only inbox/thread WebSocket endpoint on a separate port. Request/response shape. |

**Stays as direct calls in `startDaemon`** (side-effect-only at startup, no exports anyone needs to depend on): `safety-nets`, agent discovery, `killStaleTeamroomContainers`, PID file write, port file writes.

### Dependency direction (deliberate)

```
observability  ← (everyone)
storage        → observability
messaging      → observability
mcp-mail       → storage, messaging, observability
model-proxy    → observability
session-mgmt   → messaging, observability  (+ DockerRunner)
channels       → messaging, mcp-mail, observability
queries        → storage, observability
```

The notable arrow: **`channels` → `mcp-mail`**. Inbound CLI chat goes through `MailDispatcher.sendMail()` rather than around it. The dispatcher is the entry point for creating mail rows and publishing dispatch events; channels is a *transport* that depends on the *messaging system* it's transporting for.

## Channel architecture

A **channel** is a routing prefix bound to an authentication policy. The daemon's `chat` WebSocket endpoint is the bus-to-external bridge; per-channel external integrations (CLI command today; future Telegram gateway, Slack gateway) live as **separate processes** that connect to the WebSocket as clients.

### What's inside the daemon

- `ChannelRegistry` — a small in-process registry of channel names ("cli", future "telegram") and their auth policies. No bespoke per-channel adapter code.
- `chat` WebSocket endpoint — clients connect, authenticate for a channel + external ID, receive bus events addressed to `channel:<their-channel>:<their-id>`, publish inbound mail.
- Bus subscription that routes outbound `channel:*` mail to the matching connected client.

### What's outside the daemon

- `teamroom chat` / `teamroom inbox` / etc. — terminal binary; WebSocket client.
- (Future) Telegram gateway — separate process; speaks Telegram API on one side, daemon's chat WebSocket on the other.
- (Future) Slack gateway — same shape.

The daemon doesn't know about Telegram or Slack specifically. It just knows about channels named "telegram" and "slack" and where to route their mail.

## Address scheme

Hierarchical, three top-level kinds:

```
agent:<name>                       e.g. agent:claude-assistant
list:<name>                        e.g. list:harness-activity
channel:<channel>:<external-id>    e.g. channel:cli:don
                                        channel:telegram:12345
```

`Address` discriminated union:

```typescript
type Address =
  | { kind: "agent"; name: string }
  | { kind: "list"; name: string }
  | { kind: "channel"; channel: string; externalId: string };
```

**Validation.** `parseAddress` accepts well-formed addresses regardless of channel-registry state (lenient parse). Delivery-time validation in the dispatcher rejects channel addresses whose `channel` isn't in the registry (strict deliver). Mirrors how email itself works — you can write `bob@example.com` regardless of whether SMTP can deliver it; the failure is at send time.

### Migration (DB)

Migration `004_channel_address_scheme`. `from` is a single string column; `to` and `cc` are TEXT columns holding JSON arrays of address strings. The migration:

- For `from`: simple SQL `UPDATE messages SET "from" = 'channel:cli:' || substr("from", 5) WHERE "from" LIKE 'cli:%'`.
- For `to` / `cc`: walk JSON arrays element-wise. Done in TypeScript inside the migration runner (SQLite's `json_each` is read-only and can't rewrite in place safely across the column). Read each row with a `cli:`-prefixed element, parse the JSON array, transform each element with `cli:` prefix to `channel:cli:`, write back. Idempotent — re-running rewrites zero rows on the second pass.

Test fixtures and any inline `cli:*` references across `src/` and `tests/` are updated in the same change set as part of the address-scheme work.

## Port-file convention

`<dataDir>/ports/<surface>.port` for every daemon-opened HTTP/WebSocket port. One file per port; one line containing the port number; deleted at shutdown.

```
data/ports/mail-mcp.port
data/ports/model-proxy.port
data/ports/chat.port          (new)
data/ports/queries.port       (new)
```

**Agent containers** continue to receive the mail-MCP port via the `TEAMROOM_MCP_URL` env var injected by the daemon at container start (the daemon controls the container's environment; env-var injection is cleaner than file mounting). **User-started CLI tools** read the port files (the user's shell doesn't inherit the daemon's env; files are the canonical unix pattern).

## External surfaces

Both new daemon surfaces use **WebSocket** as the transport, with separate ports and separate port files. WebSocket is the standard for bidirectional Node↔client communication in 2026; the `ws` library is mature and lightweight; native `http.Server` upgrade path keeps deps small. `queries` only uses one direction today but uses the same transport for consistency and to keep the read-write evolution open.

### `chat` WebSocket — bidirectional bus interaction

**Client → daemon messages:**

- `register` — `{ type: "register", channel: "cli", externalId: "don" }`. Establishes which channel-address the client owns for this connection.
- `publish` — `{ type: "publish", to: ["agent:foo"], body: "...", threadId?: string | null, cc?: string[] }`. Inbound mail. Daemon calls `dispatcher.sendMail({ from: "channel:<channel>:<externalId>", to, body, threadId, cc })`.

**Daemon → client messages:**

- `mail` — `{ type: "mail", id, from, to, cc, body, threadId, ts }`. Outbound mail addressed to the client's channel address.
- `event` — `{ type: "event", event: "session.idle_exit" | "session.spawned" | ..., payload }`. Selected bus events the client subscribed to (TBD in implementation; minimum set deferred unless a use case forces it now).
- `error` — `{ type: "error", code: "thread_cap_exceeded" | "invalid_recipient" | ..., message }`. Structured errors with machine-readable codes.

### `queries` WebSocket — read-only request/response

**Client → daemon messages:**

- `query` — `{ type: "query", id, query: "inbox" | "thread", params: { ... } }`.

**Daemon → client messages:**

- `result` — `{ type: "result", id, rows: [...] }`. Matched by `id` to the request.
- `error` — `{ type: "error", id, code, message }`.

## CLI commands

| Command | Behavior | Transport |
|---|---|---|
| `teamroom serve` | Start daemon. | (daemon process) |
| `teamroom status` | Daemon status. | reads PID file + ports/ |
| `teamroom send <agent> "<text>"` | Fire-and-forget send. Useful for scripting. | chat WebSocket (publish, no wait) |
| `teamroom chat <agent> "<text>"` | Send and wait for reply. Prints reply(s) and exits. | chat WebSocket (publish + wait) |
| `teamroom inbox <agent>` | List agent's inbox. | queries WebSocket |
| `teamroom thread <id>` | Show a thread. | queries WebSocket |

**`chat` exit conditions:** prints reply and exits 0 when the target replies addressed to the user's `channel:cli:<user>` (success). Exits 0 if the target's session goes idle without replying ("no reply" — informational). Exits non-zero on timeout (configurable via `--timeout`, default 60s) with structured error.

**Removed:** `tail`.

## Composition pattern

`startDaemon` becomes a thin top-level composer:

```typescript
export async function startDaemon(opts: DaemonOptions): Promise<StartedDaemon> {
  // Side-effect-only startup
  await safetyNets(opts);
  await killStaleContainers();
  writePidFile(opts);

  // Modules
  const obs = composeObservability({ dataDir: opts.dataDir });
  const storage = composeStorage({ dataDir: opts.dataDir, obs });
  const messaging = composeMessaging({ obs });
  const agents = await discoverAgents(opts.agentsDir, storage.agentRepo, obs);
  const mcpMail = composeMcpMail({ storage, messaging, obs, agents, lists: loadListsYaml(...) });
  const modelProxy = await composeModelProxy({ obs, lmStudio: opts.lmStudio, anthropic: opts.anthropic });
  const sessionMgmt = composeSessionManagement({ messaging, obs, runner: new DockerRunner(), spec: buildSpec(...), idleMinutes: ... });
  const channels = await composeChannels({ messaging, mcpMail, obs, port: 0 });
  const queries = await composeQueries({ storage, obs, port: 0 });

  // Port files
  writePortFiles(opts.dataDir, { mailMcp: mcpMail.port, modelProxy: modelProxy.port, chat: channels.port, queries: queries.port });

  return { stop: composedStop([channels, queries, mcpMail, modelProxy, sessionMgmt, messaging, storage]), ...exports };
}
```

`composeIntegrationHarness` calls the same `compose*` functions with test-friendly substitutions (`:memory:` DB, `ControllableClock`, `FakeRunner`, deterministic IDs, manual timers). Test scripts patch `runner.start` after the session-management module is composed.

**Composition parity is delivered by construction**: the wiring shape is the same function-call sequence in both paths, so the M4 bug class (subscription wired in test harness, missing from `startDaemon`) cannot recur.

## Data flows

### Agent → Agent (MCP)

1. Agent A's container calls `mcp-mail`'s MCP server: `mail.send({ to: ["agent:b"], body: "..." })`.
2. MCP tools call `MailDispatcher.sendMail()`.
3. Dispatcher writes mail row to `storage`, publishes `mail.delivered` on `messaging`.
4. `session-management` consumes `mail.delivered`, wakes Agent B's session.

### Agent → channel (MCP)

1. Agent A's container: `mail.send({ to: ["channel:cli:don"], body: "..." })`.
2. Dispatcher writes mail row, publishes `mail.delivered`.
3. `channels` module consumes `mail.delivered` for `channel:*` recipients, looks up the active client connection for `channel:cli:don`, forwards as a `mail` WebSocket message.

### CLI user → agent (chat command)

1. User runs `teamroom chat agent-x "hello"`.
2. CLI binary opens chat WebSocket, sends `register` then `publish`.
3. `channels` module receives `publish`, calls `MailDispatcher.sendMail({ from: "channel:cli:don", to: ["agent:agent-x"], body: "hello" })`.
4. Dispatcher writes mail row, publishes `mail.delivered`.
5. `session-management` wakes Agent X's session.
6. Agent X replies; goes through Agent → channel flow back to the connected CLI client; CLI prints and exits.

### CLI user → inbox (inbox command)

1. User runs `teamroom inbox agent-x`.
2. CLI binary opens queries WebSocket, sends `query`.
3. `queries` module reads `MessageRepo.listInbox("agent-x")`, returns `result`.
4. CLI prints rows and exits.

## §15a — MCP SDK retrofit

`src/mail-mcp/server.ts` (currently hand-rolled JSON-RPC over `node:http`) is replaced with `@modelcontextprotocol/sdk`'s `McpServer` + `StreamableHTTPServerTransport`. Tools registered via the SDK's tool API; server hosted in-process on the same port (no boundary change). The `/cli/send` sibling endpoint is **removed** (CLI no longer talks to mail-MCP).

The 15 server-side tests migrate: token-auth assertions, tool-call semantics via `MailMcpTools`, and the pure-MCP tool surface. The CLI-endpoint tests are dropped (the endpoint is gone). New tests cover SDK-shaped tool registration and SDK-shaped error envelopes.

**Why now:** memory rule `feedback_teamroom_protocol_sdk_default` ("hand-roll only with a documented blocker-grade reason") + M4 retro §2 ("hand-rolling the MCP server side was false economy"). Bundle with the channel work because both touch the same files and we want to pay the test-migration cost once.

## Testing

### Module-level

Each `compose*` function is testable in isolation with in-memory deps. Module test files live alongside the module: `src/modules/mcp-mail/mcp-mail.test.ts` etc. Existing tests under their original paths migrate to the modules layout.

### Composition parity (by construction)

`composeIntegrationHarness` and `startDaemon` both call the same `compose*` functions. The wiring shape is identical by construction. No snapshot test required — the M4 bug class is structurally prevented.

### Acceptance scenarios

The seven scenarios from §15 followups are the manual-validation criteria for M4.5. They are run via the new CLI commands rather than the prior tail-and-send-from-second-window dance:

1. **`ccAll` group thread** — three-party thread stays coherent; `chat` reaches all participants.
2. **Thread cap (default 10)** — 11th send returns a clean structured error via the chat WebSocket.
3. **Idle exit** — `TEAMROOM_SESSION_IDLE_MINUTES=1`, send one mail, wait 2min, verify `docker ps` shows session gone.
4. **Daemon-restart kills stale containers** — start daemon, send mail, Ctrl-C, restart, verify previous container killed at startup.
5. **Self-mail** — agent mails itself; no deadlock.
6. **Concurrent spawn** — two `chat` commands to different agents simultaneously; both spawn without MCP-token collision.
7. **Invalid recipient** — agent mails a bogus address; structured MCP error surfaces to the LLM.

These are validated manually by running the new CLI commands. They do not become automated tests in M4.5 (per `see-only-as-far-as-needed` — formalize when a second sighting forces it).
