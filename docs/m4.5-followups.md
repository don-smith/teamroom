# M4.5 Follow-ups

*Items deferred from M4.5 — both those explicitly carved at scope time and those surfaced during execution + acceptance. Trigger conditions noted on each entry so future brainstorms can decide when to pick them up. Items already covered in [`docs/m4-followups.md`](m4-followups.md) (e.g., second channel, durable event bus, deeper threading) are not duplicated here.*

## 1. §16 turn-event publication (`turn.started` / `turn.completed`)

`MailingListTriggerListener` + `MailingListRegistry` are wired end-to-end, but M4.5's session-driven runtime doesn't actually publish `turn.started` / `turn.completed` on the `EventBus`. `list:harness-activity` works mechanically (verified in `tests/integration/mailing-list-fanout.test.ts`, which publishes events manually) but is silent in live operation.

**Fix shape:** have `SessionTimerManager` publish `turn.started` before each `writeEnvelope` and `turn.completed` after the runtime's reply completes (or after an idle-timeout-driven stdin close). ~30 lines + test.

**Trigger:** bundled with the future "lists" milestone (see #2). The mailing-list infrastructure is in place; the trigger plumbing is the missing piece.

## 2. Mailing-list system end-to-end verification + design pass

M4.5 carved out a deeper look at lists. Today the infrastructure works mechanically (registry loads `lists.yaml`, dispatcher fans out, trigger listener exists) but live operation has never been exercised end-to-end with real subscribers receiving real fanout. Open design questions:

- Does `list` deserve a top-level address prefix alongside `agent` and `channel`? It's a delivery pattern more than a recipient.
- How do agents discover which lists they're subscribed to, and how can they subscribe/unsubscribe themselves?
- Per-list authorization policy (who can publish to a list?).
- Bundle with #1 above so live trigger events demonstrate the system.

**Trigger:** when an agent (or use case) needs lists for real coordination — e.g., a "test failures" notification list, a code-review-request list, etc. The current `list:harness-activity` is speculative; without a concrete consumer the design questions stay academic.

## 3. Mail-MCP / daemon coupling architectural review

M4.5 reshaped the daemon into a thin composer over named modules, and lifted the mail substrate into `composeMcpMail`. The mail-MCP HTTP server still lives in-process within the daemon (same trust boundary, no IPC). The architecture is correct for now, but the option to run mail-MCP as a separately-addressable surface (e.g., for multi-host deployment, or to host mail-MCP without the rest of the daemon) is unexplored.

**Trigger:** a deployment scenario that wants to host mail without sessions, or a security review of the in-process trust boundary. Not urgent.

## 4. `channel.cli.out` event generalization

The dispatcher publishes `channel.cli.out` for every message addressed to `channel:cli:*`. `ChatServer.routeCliDelivery` subscribes to this event and routes to connected CLI clients. This is hard-coded to "cli" — when a second channel (Telegram, Slack, voice, etc.) lands, the dispatcher will need to either:

- (a) Publish a generic `channel.out` event with the channel name in the payload, OR
- (b) Per-channel events (`channel.telegram.out`, `channel.slack.out`) with ChatServer subscribing to all of them.

(a) is cleaner. The plan reviewer flagged this technical debt during M4.5 Group 13 — it was correctly deferred since CLI is the only channel today.

**Trigger:** a second channel (Telegram, Slack, voice) is being implemented. See [`docs/m4-followups.md`](m4-followups.md) §2 for the parent "second channel" item.

## 5. `ChannelRegistry` → dispatcher wiring (strict-deliver)

Today the `ChannelRegistry` is consulted only by `ChatServer` to validate `register` messages. The mail dispatcher accepts channel-kind addresses unconditionally — `parseAddress` is lenient, but the "strict deliver" half of the contract isn't enforced. The reviewer flagged this in the Group 14 review.

**Fix shape:** add `knownChannels: (n) => boolean` to `MailDispatcherOpts`, threaded through `composeMcpMail` deps, populated by the channels module's registry. Then the dispatcher rejects sends to `channel:bogus:*` at delivery time the same way it rejects unknown agents and lists.

**Trigger:** when the second channel lands (#4) — the wiring naturally needs the registry to know which channels exist. Could also land standalone as a hardening pass.

## 6. Cap-warning feature (agent-aware thread-cap headroom)

When a thread approaches the cap (default 40 mails post-M4.5), agents have no signal until they hit it — and the agent that sends the cap-exceeding message just gets an error, with no chance to wrap up gracefully. Acceptance feedback: the **last 10 messages** of a thread should carry a "thread approaching cap: X messages remaining" hint in the dispatcher's response so agents can see the limit coming and consolidate.

**Fix shape:** dispatcher's `mail.send` / `mail.reply` MCP tool responses include `warning: "thread_approaching_cap"` + `messagesRemaining: number` when the post-send count is at `cap - 10` or lower. Agent system prompts get updated to wrap up threads gracefully when they see the warning.

**Trigger:** sooner is better — likely a small early entry in the next milestone. The current behavior is functional but not friendly. Estimated work: dispatcher logic + MCP tool response schema + tests + AGENTS.md prompt updates. ~50 lines.

## 7. `ccAll` default on reply (multi-party thread coherence)

Acceptance found: in a chat where the user has agent A loop in agent B via `ccAll: true`, A's subsequent replies do NOT default to ccAll, so B silently drops out of the thread. The user has to explicitly remind A to keep B in the loop.

**Fix shape:** `mail.reply`'s default `ccAll` should be `true` when the thread already has multiple participants (>1 distinct from the replier). Could also be a tool-input default rather than a dispatcher policy. Either path: the spec for `mail.reply` needs to document the default explicitly.

**Trigger:** sooner is better — same milestone as #6. Both are agent-ergonomics fixes that emerged from real use.

## 8. CLI users can publish `cc` (chat WebSocket extension)

The chat WebSocket protocol's `publish` message accepts `cc: string[]`, but the `teamroom chat` REPL doesn't expose any way to set cc. CLI users can only address one agent per line; agents (via MCP) can cc others freely.

**Fix shape:** either a slash-command in the REPL (`/cc agent:bob`) that adds bob to subsequent publishes, or a header-style syntax (`@agent:bob hello to A and B`). Needs a small UX design pass.

**Trigger:** when human-driven multi-party threads become common. Today agents handle this fine — humans just have to start the conversation with one agent and let them loop in others.

## 9. `teamroom send` no-ack 30ms sleep

`src/cli/send.ts` registers + publishes + waits 30ms before closing the WebSocket. The chat protocol has no acknowledgement frame, so without the sleep the close could race the publish on a slow daemon. 30ms is fine for local loopback but brittle in slow environments.

**Fix shape:** add a tiny `ack` frame to the chat protocol — server confirms receipt of `publish` (could just echo the assigned `messageId`), and `send` waits for the ack instead of sleeping. Small protocol extension; needs server + client updates + test.

**Trigger:** if anyone reports `send` flakiness, or as part of a hardening pass on the chat protocol.

## 10. Model-proxy log readability

The daemon log is JSON-Lines. The model-proxy publishes span events that include full request/response context (prompts, response text). When tailed in a raw terminal, embedded JSON containing message bodies makes the log hard to scan even though it's structurally valid.

**Fix shape:** options include (a) truncate long fields in the log (e.g., body fields > 200 chars become `"<truncated 1234 chars>"`), (b) a verbose-mode flag to opt into full logs, (c) a `teamroom logs` pretty-printer subcommand that reads the JSONL and renders a human-friendly view, (d) split high-volume span events to a separate file.

**Trigger:** anyone wanting to debug LLM interactions and finding the raw logs unreadable. Not blocking; structured logs are still queryable via `jq` etc.

## 11. `teamroom status` enrichment

Post-M4.5, `teamroom status` shows the daemon PID + the three port files. With the legacy turn counts gone, the command surface is honest but minimal. Could be enriched to show:

- Active session count + per-agent state (alive / idle / waiting)
- Last-mail-delivered timestamp (to confirm the substrate is actually flowing)
- Connected channel clients (which `channel:cli:*` registrations are live on the chat WebSocket)
- Mail-MCP server health (any recent auth failures, etc.)

**Trigger:** when operators want a quick "is it healthy?" command beyond grepping logs. Likely small daemon-side query API + a richer formatter.

## 12. WebSocket protocol parser dedup

`src/modules/channels/protocol.ts:parseClientMessage` and `src/modules/mail/protocol.ts:parseClientMessage` share validation scaffolding (object-shape narrowing, type-discrimination, error message style). A tiny shared helper (`expectString`, `expectStringArray`) would shrink both files modestly.

**Fix shape:** add `src/modules/protocol-helpers.ts` (or similar) with the few generic narrowing helpers; refactor both parsers to use them. Pure cleanup; no behavior change.

**Trigger:** when a third WebSocket protocol lands (or when one of the two parsers needs a non-trivial change and the duplication makes the diff awkward).
